# Architecture Decision Records (ADR)

Append a short ADR whenever you make a decision that shapes structure, dependencies, security, or the tenancy/local-first model. Format: Context → Decision → Consequences → Status.

## ADR-0001 — Build on the Tauri/Rust core, treat the Python backend as legacy
**Context:** Meetily's supported app is the Tauri (Rust) + Next.js client; the Python/FastAPI `backend/` is archived with unauthenticated CORS.
**Decision:** Build the product on the Tauri core. Do not depend on the legacy backend at runtime; use it as reference (schema/prompts) only. The future server is a NEW clean service.
**Consequences:** One authoritative capture/transcribe/summarize path; a clean, secure server later; some reference code stays unused.
**Status:** Accepted.

## ADR-0002 — Local-first, server-optional, tenant-aware-by-design
**Context:** We want enterprise + eventual multi-tenant SaaS without losing the local-first (privacy) value prop.
**Decision:** Ship single-tenant/local first; introduce the four seams (AuthContext, tenant_id on all entities, repository layer, dormant sync) from Phase 1. Server is additive.
**Consequences:** Phase 2 is additive, not a rewrite; a little upfront discipline (tenant_id, repositories) in Phase 1.
**Status:** Accepted.

## ADR-0003 — Server language: Rust/Axum
**Context:** Options: Rust/Axum (cohesion with the core, shared models) vs clean FastAPI (velocity, reuse legacy schema/prompts as reference). Decided 2026-07-02 at BOOTSTRAP Step 3, per the default recommendation in docs/ARCHITECTURE.md.
**Decision:** **Rust/Axum** for the Phase-2 sync/collaboration server. Rationale: one language across core+server (the docs/CONTRACTS.md types — AuthContext, Repository, sync protocol — map 1:1 to shared Rust types instead of being re-modeled in Python), one toolchain (already proven on this repo), no second runtime to secure/operate, and the archived FastAPI backend stays reference-only for schema/prompts. FastAPI remains the sanctioned fallback ONLY if Rust server iteration proves measurably slow.
**Consequences:** `server/` (Phase 2, task D1) scaffolds as Axum + Postgres (RLS) with OIDC at the gateway; shared entity types live in a workspace crate reusable by client and server; hiring/onboarding assumes Rust.
**Status:** Accepted (re-confirm briefly at D1 kickoff before the first `server/` commit; server work does not start before gate C8).

## ADR-0004 — Audio module: `audio/` is authoritative; `audio_v2/` is dead code
**Context:** Base has both `audio/` and `audio_v2/`. Read-only investigation (audio-pipeline-engineer, 2026-07-02, Meetily v0.4.0) gathered wiring/runtime/history evidence.
**Decision:** **`frontend/src-tauri/src/audio/` is the authoritative module.** `audio_v2/` is an abandoned v0.1.1 rewrite scaffold, **not compiled into the binary**: no `mod audio_v2;` anywhere (`lib.rs:40` declares only `pub mod audio;`), zero `crate::audio_v2::` references (vs **59** refs to `crate::audio::` across 21 files), zero `#[tauri::command]` entry points (all ~30 registered audio commands come from `audio::`), and it is bit-rotted (imports `crate::audio::core::*` which no longer exists; duplicate `MixingMode`; undefined `AudioStream`). Git: `audio/` 125 commits (active through v0.4.0); `audio_v2/` exactly 1 commit (2025-10-23, v0.1.1) then never touched; 19 TODO/"Phase N" stubs in 1,393 LOC. Live-session log targets (`app_lib::audio::pipeline`, `::vad`, `::transcription::worker`) confirm `audio/` is the executing pipeline. The improvements audio_v2 promised (simplified pipeline, EBU R128) were since implemented inside `audio/` itself (`audio/mod.rs:18-26`, `audio_processing.rs`).
**Consequences:** No convergence flag is needed — nothing reachable to converge. `audio_v2/` is FROZEN (no new code, no imports). Delete it in a dedicated audio-cleanup ticket **after the Phase-0 validation gate passes**, together with the other verified-unreferenced dead files (`src/lib_old_complex.rs`, `src/audio/core-old.rs`, `src/audio/recording_saver_old.rs`), followed by `cargo build` + one recording smoke test per platform. All audio work targets `audio/` and routes to audio-pipeline-engineer.
**Status:** Accepted.

## ADR-0010 — Tenant-scoped repositories are the only storage access path (BACKLOG B2 phase 2)
**Context:** Phase 1 (migration `20260702000000`) added `workspace_id` + sync columns to every domain table; B1 added the `AuthContext` seam. The repositories still ran unscoped SQL, and stray SQL existed outside `database/` (`api/api.rs` `open_meeting_folder`; `audio/import.rs` meeting+segment inserts and settings read; `audio/retranscription.rs` transcript delete/insert and two settings reads).
**Decision:** Every public method of the five repositories (`meeting`, `transcript`, `summary`, `transcript_chunk`, `setting`) takes `ctx: &AuthContext`; every SELECT/UPDATE/DELETE is scoped by `workspace_id = ctx.tenant_id`; every INSERT sets `workspace_id` and populates `created_at`/`updated_at` (nullable on `transcripts`/`transcript_chunks`/settings tables); every write to a synced table bumps `rev` and stamps `updated_by`. Commands and background tasks resolve identity **only** via `crate::context::current()` (never from the frontend — `AuthContext` is deliberately not `Deserialize`). Stray SQL was routed through repository methods; two methods were added for the audio flows (`create_meeting_with_segments` — preserves caller segment ids; `replace_meeting_transcripts` — transactional delete+insert with a scoped meeting-existence check) and one projection (`get_transcript_provider_model`). Timestamp writers standardized on binding `chrono::DateTime<Utc>` (RFC 3339); the one `naive_utc()` outlier (`update_meeting_title`) was fixed. Reads do **not** filter `deleted_at` yet — the app has only hard-delete flows today; soft-delete semantics land with sync.
**Settings caveat:** `settings`/`transcript_settings` keep the legacy single-row `id = '1'` PRIMARY KEY, which collides across workspaces. Until a Phase-2 migration widens the key to `(id, workspace_id)`, their upserts guard `DO UPDATE ... WHERE workspace_id = excluded.workspace_id`, so a foreign workspace's write degrades to a no-op instead of clobbering another workspace's row (proven by test). Single-workspace local mode is unaffected.
**Consequences:** `grep` for `sqlx::query` outside `database/` is now a valid review gate (`/tenant-check`); local flows are behavior-identical (everything is workspace `local`); cross-workspace isolation is proven by `frontend/src-tauri/tests/repository_tenant_scoping.rs` (6 integration tests, both directions). `rev` now increments on local edits — correct "modified since baseline" state for future sync.
**Phase-2 rules (guardian review, 2026-07-02):** (a) when `context::current()` becomes request-scoped, spawned background tasks must receive the `AuthContext` **captured at command time** — they must not re-resolve `current()` inside the task (today's constant resolver makes both equivalent; the spawn site in `summary/commands.rs` carries a `// Phase 2:` marker). (b) Repository no-match results (`Ok(false)`/0-rows on cross-workspace access) map to **404** at Phase-2 server endpoints, and status-writer methods (`update_process_completed/failed/cancelled`) must check `rows_affected` server-side rather than returning unconditional success.
**Status:** Accepted.

## ADR-0011 — BYOK LLM/STT API keys live in the OS credential store, not SQLite plaintext
**Context:** CLAUDE.md §0.7/§3 and `docs/SECURITY_PRIVACY.md` ("Secrets") require BYOK keys to live in the OS keychain / secure store — never SQLite plaintext, source, or logs. The Meetily base stored provider keys in plaintext `*ApiKey` columns of `settings` / `transcript_settings` (flagged by the guardian security review). This is a standalone secrets fix; **it is not** the SQLCipher at-rest DB-encryption work (BACKLOG B3, deferred — that will be a later ADR and encrypts the whole DB file; the two are independent and complementary).
**Decision:** Introduce a `secrets` module (`frontend/src-tauri/src/secrets.rs`, registered in `lib.rs`) wrapping the `keyring` crate (v3.6.3; native backends only — Windows Credential Manager via `windows-native`/`windows-sys` pure-winapi, macOS Keychain via `apple-native`, Linux keyutils via `linux-native`; no dbus/openssl build-time toolchain, works fully offline). Service name = `com.bluedev.mityu`; entry name = `{tenant_id}:{summary|transcript}:{provider}:api_key` — **workspace-scoped** (tenant-aware-by-design; a future non-`local` workspace cannot read another workspace's key, identity from `AuthContext` only) **and domain-scoped** (so the two settings tables' shared provider names `openai`/`groq` do not collide). All secret functions take `&AuthContext`, return `anyhow::Result` with context, **never log key values**, and **fail closed** — a locked/unavailable store yields a user-facing error with **no silent plaintext fallback**.
`SettingsRepository::save_api_key`/`save_transcript_api_key` now write the secret to the credential store first (abort before touching the DB if it fails), then persist only the non-secret marker `keychain:v1` in the legacy column; `get_api_key`/`get_transcript_api_key` read from the credential store; `delete_api_key` clears both. The columns are **kept** (not dropped) for schema/older-binary compat and to carry the reference marker. The existing Tauri command signatures/return types are unchanged, so the Next.js UI keeps working through the same `invoke()` calls with no `frontend/src` edits.
A one-time migration `migrate_plaintext_keys_to_keychain` runs inside `DatabaseManager::new` (covers fresh/legacy-import/recovery init paths) and lazily on first read: for any column still holding a real key (present, non-empty, not the marker) it moves the value into the credential store and overwrites the column with the marker. It is **idempotent**, receives the resolved `AuthContext` and touches **only that authorized workspace**; a future authenticated workspace switch reruns the same scoped migration/lazy read instead of enumerating or synthesizing identities for other workspaces. It runs **offline** and is **non-fatal** for keychain availability — if the credential store is unavailable, plaintext is scrubbed and that provider requires user re-entry, so the app still opens the DB and works offline (local-first invariant).
**Consequences:** No provider key is ever persisted in SQLite again; local single-`local`-workspace behavior is byte-identical for the user (a previously-saved key still calls providers after migration). The `geminiApiKey` column (schema-present but not yet wired to a provider) is swept defensively. `keyring` is now a dependency (and dev-dependency, so integration tests can install a persistent in-memory credential store — keyring's built-in `mock` is `EntryOnly` and cannot model separate `Entry::new` set→get calls). Tests never touch the real machine credential store. **For the SQLCipher (B3) agent:** `keyring 3.6.3` is already in `Cargo.toml`; B3 encrypts the DB file at rest and is orthogonal to this — the `*ApiKey` columns will by then hold only the marker, so no plaintext secret is exposed even in the pre-encryption DB.
**Status:** Accepted.

## ADR-0012 — Dormant sync client seam (BACKLOG B4): typed, disabled, no network, apply-remote bypasses the Phase-1 repositories
**Context:** ADR-0002 mandates a **dormant sync client** as one of the four Phase-1 seams so Phase 2 (the optional `server/`, ADR-0003 Rust/Axum) is additive, not a rewrite. `docs/CONTRACTS.md` §5 pins the wire shapes; `docs/DATA_MODEL.md` defines the sync semantics (monotonic `rev`, `updated_by`, soft-delete `deleted_at`; client SQLite authoritative for a user's own captures) and the never-synced baseline (`rev = 1` + `updated_by IS NULL`); `docs/MULTITENANCY.md` classifies data as local-only vs synced (`provider_credential` secrets NEVER sync). The seam must exist and be typed **without** breaking the local-first invariant: the app must behave byte-identically with sync off, and **no** network dependency may be added (no `reqwest`/`tokio-tungstenite`).
**Decision:** Add `frontend/src-tauri/src/sync/` (`mod.rs` / `protocol.rs` / `client.rs`, per `docs/SCAFFOLD.md`), registered as `pub mod sync;` in `lib.rs`. It is **inert**: no Tauri command is registered, nothing on the capture→transcript→summary→store path calls it, and there is no UI toggle. Reuses only already-present deps (serde, serde_json, uuid, chrono, thiserror, anyhow).
- **`protocol.rs`** — the §5 wire types with serde: `SyncEntity { Meeting, Transcript, Summary, ActionItem }` (`#[serde(rename_all = "snake_case")]` ⇒ tokens `meeting|transcript|summary|action_item`), `PushItem { tenant_id, entity, id, rev: u64, updated_by: Option<String>, updated_at, deleted: bool, payload: serde_json::Value }`, and `ServerAck { id, server_rev: u64, conflict: bool }`. Struct field order matches §5 so the serialized key order matches the documented sample; round-trip/shape tests assert the exact key SET, ORDER, and value types against JSON literals transcribed from §5, and parse the §5 doc samples back. `updated_by` is `Option` so the never-synced baseline serializes as `updated_by: null` (no sentinel user id).
- **`client.rs`** — `SyncConfig { enabled: bool }` (`Default` derived ⇒ `false`), a `SyncClient<T: Transport = NoopTransport>` whose `push`/`pull` **guard on `enabled` FIRST and return `SyncError::Disabled` (thiserror) performing NO I/O** while disabled (proven by an atomic-flag spy transport that stays untouched). A `Transport` trait abstracts the wire; the ONLY Phase-1 impl is `NoopTransport` (reports non-operational, returns `SyncError::NoTransport` — never fabricates acks), so the Phase-2 HTTPS transport slots in as a new impl behind a flag without changing this file. `SyncError` also pre-defines `NoTransport`/`Transport(String)`/`Protocol` for a stable Phase-2 surface.
- **CRITICAL seam — `RemoteApply` (guardian-flagged):** applying a PULLED remote change MUST NOT go through the Phase-1 repositories (ADR-0010), because those bump `rev = rev + 1` and stamp `updated_by = ctx.user_id` on **every** write. Replaying a remote change through them would (1) masquerade it as a local edit (`updated_by` = local user), (2) re-bump `rev` and destroy the server-assigned `rev` and the `rev = 1 / updated_by NULL` never-synced baseline, and (3) make the row look "modified since sync" again → the next push re-sends it, the server re-acks, forever (a ping-pong / infinite echo). So `apply_remote` is a **distinct trait** (defined, not wired) whose contract — captured in rustdoc — is to write `rev`/`updated_by`/`updated_at`/`deleted_at` **VERBATIM** from the `PushItem` payload (a future dedicated "remote-apply" repository path with its own `... ON CONFLICT DO UPDATE SET rev = :remote_rev, updated_by = :remote_updated_by, ...` SQL), passing `AuthContext` for **tenant scoping only**, never to derive identity/rev. A unit test encodes this as an executable check (a recording `RemoteApply` impl preserves a remote author + rev, distinct from `ctx.user_id`).
- **Classification (local-only vs synced):** `SyncEntity` enumerates only the four `Synced? = yes` domain entities. There is deliberately **no** `Settings`/`Credential` variant, so a `PushItem` for `settings`/`transcript_settings` or a `provider_credential` secret cannot even be constructed — the local-only/secret boundary is structural, not disciplinary. Only a non-secret label may ever sync (a future, separate decision).
**Consequences:** The seam is typed and reviewable; Phase 2 fills in the `push`/`pull` bodies, adds an HTTPS `Transport`, and implements `RemoteApply` as a separate repository path (never a method on the existing `database/repositories/` types). Local-first holds: with sync off (always, today) behavior is byte-identical and offline; no network crate was added. DoD verified: `cargo build -p mityu` green; `cargo clippy -p mityu --all-targets` unchanged at the 142-warning baseline (the one initial `derivable_impls` finding on `SyncConfig::Default` was resolved by deriving `Default`); `cargo test -p mityu` passes (12 new sync tests + existing suites); sync files `rustfmt`-clean.
**Status:** Accepted (re-confirm the wire shapes against `server/` at D1 before the first sync endpoint).

## ADR-0013 — On-device AI agents: local-first, draft-only (HITL), no autonomous actions (EPIC F seam)
**Context:** The About screen advertises "Coming soon: a library of on-device AI agents — automating follow-ups, action tracking." That was marketing ahead of the plan: BACKLOG had **source-linked summaries (C1)** and **action-item extraction (C2)** but no "agents" epic and no "automated follow-up" capability. Building agents naively (autonomous send, cloud round-trips, auto-approval) would violate `CLAUDE.md` §0.1 (local-first), §0.5 (HITL for every AI output), and §10 (no autonomous irreversible actions). Separately, the About "Works everywhere — Google Meet / Zoom / Teams" is **not** an API integration and is intentionally absent from the plan: the app captures **system audio** (WASAPI loopback / BlackHole), recording any call online or offline — `CLAUDE.md` §1 "not a meeting bot that joins calls" stands.
**Decision:** Introduce **BACKLOG EPIC F** and scaffold a **dormant `agents/` seam** now (`frontend/src-tauri/src/agents/` = `mod.rs` + `draft.rs` + `engine.rs`, `pub mod agents;`), following the ADR-0012 dormant-`sync/` precedent (typed, disabled, no network dependency, tests pin the invariants). Reuses only already-present deps (serde, serde_json, thiserror). Four rules, encoded structurally (not merely documented):
1. **Local-first / dormant:** no LLM/HTTP client in the seam; Phase-F agents reuse the existing summary providers (`summary/` + anthropic/openai/groq/ollama/openrouter, BYOK, offline) behind the `Agent` trait (Phase-1 impl = `NoopAgent`, no I/O). Off by default (`AgentsConfig { enabled: false }`, `Default` derived) ⇒ a build is byte-identical to one without the module.
2. **HITL:** an agent run yields an `AgentDraft` whose status `AgentRunner::run` forces to `Draft`; approval is a separate human action. A self-approving agent cannot bypass it (pinned by `run_forces_hitl_never_returns_approved`). `run` guards on `enabled` FIRST and returns `AgentError::Disabled` doing no work (an atomic-flag spy proves the agent is never touched — the same pattern as sync).
3. **No autonomous external actions:** agents only *propose* — `ProposedAction` is data; there is **no** execute/send method anywhere in the seam. "Send"/"create" stays a manual user step (`CLAUDE.md` §10).
4. **Source-linked + tenant-scoped:** every output carries `SourceRef` (→ `source_chunk_id`, C1) and `ctx: &AuthContext`; `AgentRun` carries the §6 sync-ready fields (`id`, `tenant_id`, `created_at`/`updated_at`, `updated_by: Option`, `rev`, soft-delete) so a Phase-2 `agent_runs` table + sync are additive — with no `SyncEntity` coupling yet (agents don't sync until a separate decision).
Sequenced **after gate C8**, dependent on **C1 + C2**; trigger model manual/on-demand first, scheduling only at F5 behind explicit opt-in.
**Consequences:** The "Coming soon" copy is now backed by a tracked, gated plan (BACKLOG F0–F5) and an inert, tested seam that ships today without changing behavior or adding a runtime dependency. Verified here with `rustfmt` (all three files parse clean & formatted); the full `cargo build -p mityu` / `clippy` / `test` gates run in an environment with the LLVM/CMake toolchain (BOOTSTRAP Step 1). The seam's `#[cfg(test)]` invariant tests mirror `sync/`'s and only compile under `cargo test`, so a test issue cannot break `tauri:dev`. Revisit trigger/automation policy at F5 before any scheduled run ships.

## ADR-0014 — Encryption at rest (SQLCipher): key in OS keychain, one-time plaintext→encrypted conversion
**Context:** `docs/SECURITY_PRIVACY.md` ("Encryption — At rest (client): SQLCipher (encrypted SQLite) for sensitive data; OS-protected key") and BACKLOG B3 require the local SQLite DB to be encrypted at rest with an OS-protected key, while the app must **still open existing data** (documented migration path) and stay **local-first** (works fully offline; a key/store failure must never silently downgrade to plaintext). ADR-0011 already moved BYOK provider secrets out of SQLite into the OS keychain and explicitly deferred whole-file DB encryption to B3 (the two are orthogonal and complementary — after B3 the `*ApiKey` columns still hold only the `keychain:v1` marker, so even the pre-encryption backup exposes no provider secret). Feasibility was proven in a prior Step-1 spike: `sqlx 0.8.6` → `sqlx-sqlite` pulls `libsqlite3-sys 0.30.1`, which ships a `bundled-sqlcipher-vendored-openssl` feature, and sqlx treats the SQLCipher `key` pragma as a reserved first-executed slot.
**Decision:** Encrypt the whole `meeting_minutes.sqlite` file with SQLCipher (AES-256), keyed by a device-scoped 256-bit key held in the OS credential store.
- **Cargo (two dep changes):** (1) declare `libsqlite3-sys = { version = "0.30.1", features = ["bundled-sqlcipher-vendored-openssl"] }` as a **direct** dependency purely to enable the feature — Cargo unifies it with sqlx's transitive `bundled` on the same crate version, so sqlx links a SQLCipher-capable libsqlite3; no system OpenSSL/SQLCipher toolchain is needed (the vendored OpenSSL + SQLCipher amalgamation compile from source, one long native build). (2) declare `zeroize = { version = "1.8", features = ["alloc"] }` (already in-tree transitively at 1.8.2, so it unifies with no new crate) to scrub the DB key hex from memory (security-review hardening, below).
- **Key management (`secrets::db`, reuses ADR-0011's `keyring` 3.6.3):** a new `db` submodule in `secrets.rs` stores/reads the DB key under service `com.bluedev.mityu`, entry `db-key`. Unlike BYOK keys it is **device-scoped, not workspace-scoped** (one encrypted file spans all workspaces). `get_or_create_hex()` generates 32 bytes from the OS CSPRNG (`rand` 0.8, already in-tree) on first launch, stores them as 64 lowercase hex chars, and reads them back on every startup — fully offline. The key value is **never logged**; a malformed stored value is rejected (never silently regenerated — that would strand decryptable data); the value is passed to SQLCipher as a **raw** key `PRAGMA key = "x'<hex>'"` (no KDF). The key hex is returned as `zeroize::Zeroizing<String>` and held that way in `database::manager` (dropped right after the pool opens), so the material is scrubbed from freed heap rather than lingering.
- **Keyed pool (`database/manager.rs`) — GUARDRAILED fallback (revised 2026-07-03):** the main pool moved from `SqlitePool::connect(path)` to `connect_with(SqliteConnectOptions…)` applying `.pragma("key", x'<hex>')` (sqlx executes the reserved `key` slot first, before any statement), and preserves the prior behavior explicitly with `.journal_mode(Wal)` + `.foreign_keys(true)` + `create_if_missing(true)`, so the existing WAL checkpoint/recovery paths (`cleanup`, orphaned-WAL retry) keep working and a fresh install is created already-encrypted. The key path is now **state-dependent, decided from the on-disk file BEFORE the key is touched** (via `encryption::is_plaintext_db`, the shared plaintext-header probe reused from `ensure_encrypted`): `absent` = no file, `plaintext` = the `"SQLite format 3\0"` header is present, `encrypted` = a file with no such header.
  - **Encrypted file ⇒ FAIL CLOSED.** The key is read with the **non-creating** `secrets::db::get_hex()` — a missing entry must **never** mint a fresh key over live ciphertext (that would strand the data behind a key that cannot decrypt it). `Ok(Some(key))` ⇒ open keyed (`ensure_encrypted` is a no-op on an already-encrypted file). Key **missing (`Ok(None)`) or store error (`Err`)** ⇒ return a `sqlx::Error::Configuration` ("local database is encrypted but its key is unavailable … refusing to open — retry, or restore the key") and **do not open** — never a keyless open of ciphertext, never a regenerated key. This error is **distinct from corruption** (it contains neither "malformed" nor "corrupt"), so the `new_from_app_handle` WAL-recovery path is **not** entered and cannot delete the WAL of a healthy-but-locked encrypted DB.
  - **Plaintext or absent file ⇒ fail-open is permitted** (CLAUDE.md §0.1 local-first: never lock the user out of a still-plaintext file). The key is read with `secrets::db::get_or_create_hex()` (mint-on-first-run is correct here) and the file is converted via `ensure_encrypted`. If the key store is unavailable, **or** the one-time conversion fails (e.g. a SQLCipher-less runtime where `sqlcipher_export` is missing), we log **loudly and accurately** (the DB is opening **UNENCRYPTED / plaintext at rest**, will retry next launch — the log does **not** claim it is "encrypted"/"safe") and open **without** the `key` pragma. This is safe because the file was plaintext anyway, so no confidentiality is lost relative to the pre-B3 state, and **no ciphertext is ever opened keyless**.
  - This **replaces** the earlier strict "any locked/unavailable keychain aborts" wording (and reverts an interim blanket **fail-open** edit that regressed confidentiality by opening ciphertext keyless / minting a key over an encrypted file). `Zeroizing<String>` still scrubs the key hex from memory once the pool opens.
- **One-time conversion (`database/encryption.rs`, before migrations):** `ensure_encrypted()` runs in `DatabaseManager::new` **before** the keyed open and **before** `sqlx::migrate!`. It detects a plaintext DB by the `"SQLite format 3\0"` header (absent on a cipher file), then: (1) **checkpoints any plaintext `<db>-wal`** (`PRAGMA wal_checkpoint(TRUNCATE)`) so committed WAL-only rows fold into the main file and no stale plaintext `-wal` can collide with the encrypted DB's WAL; (2) opens the **encrypted destination** as the main keyed connection (create) **in rollback-journal (DELETE) mode** so the cipher DB is a single self-contained file (no `<dst>-wal`/`-shm` orphans a single-file rename would leave), `ATTACH DATABASE '<plaintext src>' AS plaintext KEY ''`, `SELECT sqlcipher_export('main','plaintext')`, `DETACH`; (3) an atomic file swap moves the original to a **temporary** `<db>.pre-encryption` backup and promotes the cipher file; (4) **verifies** the promoted file opens with the key (`SELECT count(*) FROM sqlite_master`) — and **only then deletes** the `.pre-encryption` backup (scrub-then-unlink) and any stale plaintext `<db>-wal`/`-shm`, so **no full-database plaintext lingers on disk**. If verification fails, the plaintext backup is restored and startup aborts (fail closed, recoverable). (The reverse direction — encrypted-main + plaintext-attach — is required because this `libsqlite3-sys 0.30.1` build returns `SQLITE_CANTOPEN` when `ATTACH` is asked to *create* a new encrypted file; it also mirrors exactly how the live pool later opens the keyed file, so a successful+verified conversion guarantees the pool opens it.) No row is rewritten, so every `workspace_id`/`rev`/`created_at`/`updated_at` and the **`_sqlx_migrations` ledger survive byte-for-byte** (asserted in tests). It is idempotent (no-op on an already-encrypted or missing file). The legacy `.db`→`.sqlite` import still lands plaintext first and is then encrypted by the same path.
- **Migration path for existing users:** on the next launch after upgrade, an existing plaintext `meeting_minutes.sqlite` is transparently converted once. The `.pre-encryption` backup is a **transient** safety copy during conversion and is **deleted after the encrypted DB is verified readable** — so afterwards no plaintext copy remains. Because the plaintext backup is gone and the key lives only in the OS keychain, deleting/rotating the `db-key` entry or restoring on a new machine without it makes the DB **permanently unrecoverable** — this is the intended at-rest posture (an attacker with the file but not the keychain gets nothing). A user-facing key export/rekey affordance is future work (below); until then, protecting the OS keychain is the recovery story (documented in `docs/SECURITY_PRIVACY.md`).
- **Keyless-still-reads-plaintext invariant:** a SQLCipher build with **no** `key` pragma still opens ordinary plaintext SQLite files, so the existing integration suites (`migration_workspace_sync`, `repository_tenant_scoping`) that open plain temp DBs with no key keep passing unchanged (pinned by a dedicated test).
**Consequences:** The local DB is encrypted at rest with an OS-protected key; local-first holds (offline, no network); no provider secret is exposed at any point (ADR-0011). **After a verified conversion no full-database plaintext remains on disk** (the temporary `.pre-encryption` backup and stale plaintext WAL/SHM are removed), and the DB key hex is zeroized from memory after the pool opens. Cost: one long first native build (vendored OpenSSL + SQLCipher), and the deliberate loss of any plaintext fallback for **already-encrypted** data — **the OS keychain `db-key` entry is the sole recovery path for an encrypted DB; losing it = unrecoverable data** (correct at-rest posture). Security/guardian review (2026-07-02) passed with no blocker; the three fixes applied then were: delete the plaintext backup after a verified keyed re-open (HIGH), checkpoint the plaintext WAL before conversion + remove stale plaintext WAL/SHM after (MED), and zeroize the key hex (LOW hardening).
**Guardrailed-fallback amendment (2026-07-03):** a follow-up security review found an interim edit had relaxed the keyed-open into a **blanket fail-open** — which (a) does not help an already-encrypted DB (a keyless open of ciphertext just fails or, worse, regenerating the key over ciphertext strands the data) and (b) regresses confidentiality. It is replaced by the **state-dependent** posture above: **fail-open only on a plaintext/absent file** (via `get_or_create_hex`), **fail-closed on an encrypted file whose key is unavailable** (via the non-creating `get_hex`). **Accepted local-first tradeoff:** brand-new **plaintext** data at rest is now possible **only on a machine that was never successfully encrypted** (a first run where the OS keychain is broken/locked so the key can neither be read nor minted); such a file **heals on the next launch** once the keychain is available (it is then detected as plaintext and converted). An already-encrypted DB is **never** downgraded and is **never** opened keyless. **Follow-up (tracked, NOT in this change): an in-app downgrade WARNING** surfaced to the user when the DB opens UNENCRYPTED (so a silent plaintext-at-rest state is visible), alongside the existing key export/rekey affordance and the sync/backup denylist for the encrypted file + key (deferred to B4). New tests: `frontend/src-tauri/tests/db_encryption_sqlcipher.rs` — fresh encrypted DB + migrations; plaintext→encrypted conversion preserving row counts **and** the `_sqlx_migrations` ledger (seeded via the public `Migrator`) **and** asserting the `.pre-encryption` backup is deleted; a populated-`-wal` conversion that preserves committed rows and leaves no stale plaintext `-wal`/`-shm`; wrong-key-fails-closed; the keyless-plaintext invariant; an env-gated (`MITYU_TEST_ENCRYPT_DB`) real-copy conversion proof; **and (added 2026-07-03) three `DatabaseManager::new` fallback tests driving a persistent in-memory keyring — ENCRYPTED+key-present opens & reads; ENCRYPTED+key-MISSING fails closed with the ciphertext file byte-for-byte unmodified, no new key minted, not opened as plaintext; PLAINTEXT+store-unavailable fails open (opens plaintext, rows readable, file stays plaintext).** Touched: `Cargo.toml` (the two features + the `keyring`/`tempfile` dev-deps enabling the mock keyring in integration tests), `secrets.rs` (the `db` submodule incl. the non-creating `get_hex`), `database/manager.rs`, `database/mod.rs`, `database/encryption.rs` (added the `pub fn is_plaintext_db` shared probe), the test, and this ADR + the SECURITY_PRIVACY "Encryption" note.
**Status:** Accepted (SQLCipher at-rest encryption merged; no plaintext residue after conversion; **guardrailed fallback amended 2026-07-03** — fail-open only on plaintext/absent, fail-closed on encrypted-but-keyless; revisit the in-app downgrade warning + key export/rekey + sync/backup denylist when sync (B4) or a second device lands).

## ADR-0015 — Opt-in PII/keyword redaction at the persist + summary boundaries (BACKLOG C6, redaction half)
**Context:** `docs/SECURITY_PRIVACY.md` ("Privacy & data lifecycle — Retention/redaction: ... redaction rules for PII/sensitive terms") and the OWASP LLM02 (sensitive-info-disclosure) note require per-workspace redaction of PII/sensitive terms, and `docs/DATA_MODEL.md` already lists `redaction` as a `settings` concern. `docs/SCAFFOLD.md` anticipated a `policy.rs` for per-workspace redaction. The BACKLOG C6 **retention/audio-deletion half is a separate, later change** and is explicitly out of scope here — this ADR covers **redaction only** and does **not** touch `audio/` capture internals or `audio.mp4` saving. The hard constraint: must be **non-breaking / local-first** — existing local data and flows are byte-identical unless a user opts in.
**Decision:** Add a pure, DB-free `frontend/src-tauri/src/redaction.rs` (`pub mod redaction;`) exposing `RedactionConfig { enabled, use_default_patterns, custom_terms }` (serde; `Default` = **disabled**) and `redact(text, cfg) -> String`. **OFF by default:** when `!cfg.is_active()` (the default) `redact` is a verbatim, allocation-cheap no-op. When enabled it applies built-in PII patterns and case-insensitive custom terms, each match replaced with a **typed placeholder**.
- **Default patterns (conservative — precision over recall, documented per-pattern):** email → `[EMAIL]`; IBAN (2 letters + 2 check digits + 11..30 alnum) → `[IBAN]`; credit-card (13..19 digit candidate **gated by a Luhn check**) → `[CARD]`; Turkish TC Kimlik No (11-digit candidate **gated by the official TC checksum**) → `[ID]`; phone (candidate **gated by a 7..=15-digit + leading-`+`-or-separator guard**) → `[PHONE]`; custom term (escaped, case-insensitive) → `[REDACTED]`. Fixed pass order **email → IBAN → card → TC → phone → custom** so structured numeric PII claims its digits before the looser phone pattern (a Luhn-valid card is never mangled into `[PHONE]`). The Luhn/TC/phone Rust-side validators keep ordinary long integers (ids, timestamps, non-card digit groups) from being over-redacted. Patterns compile once via `once_cell::Lazy` (both `regex` and `once_cell` were already direct deps). **No raw text or redacted-away value is ever logged.**
- **Config storage (per-workspace, tenant-scoped):** stored as a small JSON blob in a new **additive** `settings.redactionConfig TEXT` column via `SettingsRepository::{get,set}_redaction_config(ctx)` (mirrors the existing `customOpenAIConfig` JSON-column pattern; scoped by `workspace_id = ctx.tenant_id`; `get` returns the disabled `Default` when absent/unparseable so a missing/corrupt blob can never *enable* redaction). Migration `frontend/src-tauri/migrations/20260704000000_add_redaction_config.sql` is a single nullable-column `ALTER TABLE` (additive, forward-only, idempotent-by-construction like the `geminiApiKey`/`customOpenAIConfig` precedents); the `Setting` struct is untouched (sqlx `FromRow` ignores the extra column; targeted `SELECT redactionConfig` reads it). The `settings` table is PER-SCOPE and **NOT synced**, so this policy is client-local for now (a future policy-sync is a deliberate separate change).
- **Two enforcement boundaries (only when enabled; config fetched via `AuthContext`):** (1) **before persistence** — each transcript segment's `text` is redacted at the call boundary just above the repository write, keeping the repository a **pure writer** (policy is not buried in the repo). Covered persist entry points: the **main recording save** (`api::api_save_transcript`), **audio import** (`audio/import.rs`, at the `create_meeting_with_segments` text-persist boundary — redacted once so the DB rows and the on-disk `transcripts.json` stay consistent), and **retranscription** (`audio/retranscription.rs`, at the `replace_meeting_transcripts` boundary). Only `text` is rewritten; segment ids/timestamps are preserved. (2) **before the summary LLM** — `summary/service.rs::process_transcript_background` redacts the assembled `text` immediately after resolving `ctx`, before language detection, the cache fingerprint, and the provider call. This is the **key privacy boundary**: for a cloud provider it stops PII leaving the device. Because the redacted text feeds the summary cache fingerprint, toggling redaction correctly invalidates the cache (no cross-contamination of redacted/unredacted summaries).
- **Fail-safe:** if the redaction config **cannot be read** at a boundary, the operation fails with a clear, content-free error rather than persisting/summarizing potentially-unredacted PII (the persist commands return an error; the summary background task marks the process failed).
- **HITL / source-linking intact (`docs/CONTRACTS.md` §4):** redaction changes stored text only; it does not alter `source_chunk_id` linkage or the human-approved draft flow.
- **Tauri commands:** `api_get_redaction_config` / `api_set_redaction_config` (typed, registered in `lib.rs`), with a typed TS wrapper `configService.getRedactionConfig()` / `setRedactionConfig()` in `frontend/src/services/configService.ts`. The **config UI is a separate frontend task** (not built here). `RedactionConfig` is not identity, so — unlike `AuthContext` — the value legitimately round-trips through the frontend.
**Consequences:** Enterprises get an opt-in, on-device PII/keyword scrubber at exactly the two seams where sensitive text would otherwise leak (local DB at rest, and the summary provider — especially a cloud BYOK provider), with no new dependency and no change to the offline/local-first path when disabled. Conservative patterns favour missing an exotic PII shape over shredding ordinary transcript content; the placeholder taxonomy lets a reviewer see *what kind* of value was removed. Cost: one additive column/migration on `settings`; redaction is a lightweight regex pass applied only when enabled. **Out of scope / follow-ups:** the C6 retention/audio-deletion half (separate change); a config UI (separate frontend task); optional expansion of the default pattern set (e.g. IDN emails, more national-ID formats) and a future policy-sync decision. Verified: `cargo build -p mityu` green; `cargo clippy -p mityu --all-targets` at the 140 baseline with **zero new warnings**; 15 new `redaction::tests` + the full 246-test lib suite pass; rustfmt applied to the fully-owned `redaction.rs` and to only the added blocks of the shared files (no crate-wide reformat).
**Amendment (2026-07-04, commit 3b9a8ff):** the post-merge security review found a **fourth persist entry point** missing from the boundary list above: `summary/commands.rs::api_process_transcript` writes the raw frontend `text` into `transcript_chunks` (durable full-text, on the B4 sync allowlist) before the background summary task runs — so with redaction ON, un-redacted transcript could still land at rest via that path. The same redact-at-the-boundary treatment (same fail-safe) is now applied at the top of `api_process_transcript`, covering both the `transcript_chunks` write and the text handed to the summary task. Rule of thumb going forward: transcript text persists via **four** paths — `api_save_transcript`, audio import, retranscription, and `api_process_transcript` — and any transcript-wide policy must cover all four.
**Status:** Accepted (redaction half of C6 merged, OFF by default; retention half tracked separately).

- **Tier 1 — Calendar metadata (light opt-in):** read-only Google Calendar / Microsoft 365 access to enrich meetings with title/time/attendees (and optionally prompt "meeting starting — record?"). Runs entirely **on-device**: the client calls the vendor API directly, nothing transits bluedev infrastructure; OAuth tokens live in the OS keychain (ADR-0011 pattern); read-only scopes only; disconnect deletes local tokens. **KVKK assessment:** attendee names/emails are third-party personal data, but processing is client-side, for the user's own purpose, and bluedev never receives it — manageable with in-app disclosure + a privacy-policy section. **Placement decision:** although KVKK-manageable, it ships **in the Integrations section behind explicit consent**, not silently in the core flow — any external connection contradicts the "deliberately connectionless" promise unless the user chose it. (The owner may later promote it into the core flow; this ADR records the conservative default.) Earliest implementation slot: post-C8 (the ROADMAP 60–90 "one export/integration" window).
- **Tier 2 — Meeting bot (heavy opt-in, Phase 2+):** a call-joining bot for Zoom/Teams/Meet offered as an Integrations option behind an explicit terms-of-service acceptance. Hard constraints acknowledged now: it cannot be purely local (requires server-side or vetted third-party bot infrastructure → depends on EPIC D); vendor OAuth app reviews / marketplace approvals apply; the bot must announce itself in-call (vendor policy + transparency); KVKK is materially heavier — bluedev or its infra provider becomes a **data processor** for meeting audio (DPA, retention, EU residency per E2, effective consent of all participants). Honest value over Tier 0: capturing meetings the user does **not** attend, capture without the desktop app running, and per-participant server-side diarization. **This ADR fixes only the direction and the consent frame; Tier 2 requires its own detailed ADR + /security-review before any code.**
**Consequences:** CLAUDE.md §1 is refined to "not a meeting bot **by default**". ROADMAP's out-of-scope line now points here. BACKLOG gains **EPIC G** (G1 integrations hub + consent framework, G2 calendar metadata, G3 meeting bot) gated on C8 (G3 additionally on D5). Phase-1 sequencing (A5, C1–C8) is untouched. The privacy policy needs an Integrations section when G1 ships. Product story: connectionless by birth; connecting is always the user's conscious, revocable choice — competitors' convenience stays reachable without giving up the differentiator.
**Status:** Accepted (2026-07-05 — direction + consent frame; each tier's implementation still requires its own design + security review).

## ADR-0019 — C1 foundations started ahead of the A5 gate; summaries + action_items schema
**Context:** The owner explicitly instructed (2026-07-04/05) starting BACKLOG C1 ahead of the A5 Phase-0 validation gate. Scope discipline for this exception: only **transcription-quality-independent foundations** may land — the §4 draft types (C1.1, `summary/draft.rs`), the schema (this ADR / migration `20260706000000`), the repositories, and the HITL review/approve mechanics; **C1 completion and gate C8 remain gated on A5** (no structured-summary feature ships as done until Phase-0 passes). The C1 requirement itself is unchanged: every AI-generated summary block and action item is a DRAFT carrying a mandatory `source_chunk_id` back to transcript evidence (CLAUDE.md §0.5, `docs/CONTRACTS.md` §4), and `docs/DATA_MODEL.md` already promised a first-class action-item table as "a future migration".
**Decision:** Create two new SYNCED-class client tables in migration `20260706000000_add_summaries_and_action_items` (additive, forward-only, idempotent-by-construction — `IF NOT EXISTS` everywhere; documented DOWN in the header):
- **`summaries`** — ONE row per meeting (`meeting_id` UNIQUE, CASCADE on meeting delete): `status` ('draft'|'approved'), `model`, `template_id`, `sections` TEXT NOT NULL holding the §4 JSON (array of `Section{title, blocks}` with per-block `{id, type, content, source_chunk_id, status, original_content}`), `generated_at`, HITL fields `approved_at`/`approved_by`, and the full common/sync column set (`workspace_id` DEFAULT 'local', `created_at`/`updated_at`, `updated_by`, `rev` DEFAULT 1, `deleted_at`).
- **`action_items`** — many rows per meeting (CASCADE on meeting delete): `text`, `assignee?`, `due?`, `status` ('draft'|'approved'|'edited'|'rejected'), **mandatory `source_chunk_id`**, `position` (display order), `original_text` (pre-edit preservation), same common/sync column set. Indexes: `idx_summaries_workspace_meeting`, `idx_action_items_workspace_meeting`, `idx_action_items_workspace_status`.
Rejected alternatives, one line each: **reuse `meeting_notes`** — it is the dormant per-meeting *user-notes* table (human content, no HITL/source-link semantics); **extend `summary_processes`** — upstream-churn surface whose process-status lifecycle (PENDING/COMPLETED/FAILED) is orthogonal to HITL draft→approved, and its `result` JSON is the legacy shape we are superseding; **per-block rows (`summary_blocks` table)** — there is no `summary_block` sync entity (`SyncEntity` has Summary/ActionItem only), and the 1-row-per-logical-unit mapping with embedded JSON follows the `transcripts`/`meeting_notes` precedent (1:1 table↔sync-entity preferred).
**No FK on `source_chunk_id` → `transcripts(id)` (deliberate):** retranscription (`replace_meeting_transcripts`) deletes+reinserts a meeting's segment rows, so ON DELETE CASCADE would silently destroy approved evidence links and RESTRICT would block retranscription; resolvability is instead enforced at the repository layer at write- and approve-time. `meeting_id` DOES cascade (house precedent).
Five adopted implementation decisions for the C1 pipeline built on this schema: (1) the structured `summaries` row is **authoritative when the structured-summary flag is ON**, with the legacy `summary_processes.result` still written as a rollback path, and C4 exports emit **approved content only**; (2) **retranscription downgrades** that meeting's blocks/action items to `draft` (evidence re-anchoring required) with a UI warning; (3) v1 structured mode **skips the translate/normalize passes** (they operate on the legacy text path); (4) provider **JSON mode is auto-selected per provider** capability, never a user-facing setting; (5) HITL accountability via `approved_by`/`approved_at` + `tracing` logs now — a local audit **table** is deferred to the server-side append-only audit log (D2). Data classification: **draft rows are local-only sync class; approved rows become sync-eligible in Phase 2** (wire promotion is policy, per docs/MULTITENANCY.md).
**Consequences:** Older binaries are untouched (purely additive tables they never reference — sync-compatibility note in the migration header and `docs/DATA_MODEL.md`); `docs/DATA_MODEL.md`'s client table map now includes both tables (summaries ↔ sync `summary`, action_items ↔ sync `action_item`) and the "future migration" promise is fulfilled. Proven by `tests/migration_c1_summaries.rs` (fresh-DB exact shape + indexes, populated-prior upgrade preserving data with EMPTY new tables, ledger-guarded re-run no-op, CASCADE-on-meeting vs no-FK-on-chunk semantics); `db_encryption_sqlcipher.rs` `ALL_TABLES` extended 8→10. Cost: two tables exist ahead of their repositories (next C1 step); until the approve flow lands, nothing writes them.
**C1 gate review (2026-07-05):** the full C1 chain (commits `9111412..152c43f`, all six steps C1.1–C1.6) passed both gate reviews with **no blockers**. `multitenancy-guardian`: PASS — every C1 SQL statement is `workspace_id = ctx.tenant_id`-scoped (reads, writes, and `resolve_source_chunk_ids`), identity is resolver-only (`AuthContext` not `Deserialize`), `source_chunk_id` is validated resolvable at write AND re-validated at approve (cross-tenant source-injection negative test passes), generation always forces `Draft`, the "AI-generated · review required" banner is non-dismissable, and the opt-in flag is default-OFF with a byte-identical legacy path. `security-privacy-auditor`: PASS, no HIGH/MED — **no path exists where un-redacted transcript text reaches an LLM provider when redaction is enabled** (two independent fail-closed redaction gates: per-segment re-redaction in the structured branch returning Terminal/FAILED on a config-read error, plus the redacted assembled-text on the degrade-to-legacy path); BYOK keys stay keychain→HTTP-header only, logs/errors are content-free, drafts are at-rest under SQLCipher.
**Accepted, tracked Phase-2 hardening (from the gate review — not C1 blockers):** (W1) the retranscription downgrade hook runs the summaries and action-items `downgrade_to_draft` as two non-atomic statements after the replace transaction commits; if the second errors the transient state is inconsistent, but the whole call returns `Err` (retranscription reported failed), `downgrade_to_draft` is idempotent so a retry re-runs both cleanly, and approve-time source re-resolution refuses any stale-approved item on the next approve — the backstop. Make the two downgrades one transaction when the repository executor is generalized in Phase 2. (W2) `approve_summary`/block-status write-backs are read-modify-write with no `AND rev = <read_rev>` guard; unreachable under the Phase-1 single-writer local SQLite model (documented in `summary_draft.rs`), add optimistic-concurrency `rev` predicates when the Phase-2 multi-writer server lands. (LOW, out of C1 scope) a user-configured plaintext `http://` custom/Ollama provider endpoint sends over cleartext — pre-existing provider-config behavior, not introduced by C1; surface a non-TLS warning at the provider-config settings surface.
**Status:** Accepted (2026-07-05). C1 code-complete and gate-reviewed (guardian + security PASS); **feature-level "done" and gate C8 remain A5-gated** — structured-summary output quality is unproven until the Phase-0 recordings run.

## ADR-0021 — FFmpeg supply chain: self-hosted LGPL builds (Windows, Linux); macOS still open
**Context:** `docs/GA_READINESS.md` (Tier 0 #5) flagged FFmpeg as the one remaining supply-chain dependency on a third-party host, `github.com/Zackriya-Solutions/ffmpeg-binaries` — a bare mirror repo (18-byte README, no LICENSE file, no documented source) whose release body just maps platform to filename. Inspecting the actual bundled Windows binary directly (`ffmpeg -version`, run against the already-cached local copy, not a freshly downloaded one) showed `configuration: --enable-gpl --enable-version3 ... --enable-libx264 --enable-libx265 ...` and the version string `8.0.1-essentials_build-www.gyan.dev` — a **GPLv3** build (gyan.dev's naming/config match exactly), not the lighter LGPL. Grepping every FFmpeg invocation in `frontend/src-tauri/src/audio/{encode,decoder,incremental_saver}.rs` found only `-c:a aac -f mp4` (raw PCM to AAC-in-MP4) — no `-c:v`, no GPL-only codec used anywhere in this codebase. Continuing to redistribute (and now self-host under this project's own name, per the owner's explicit instruction to mirror to "my own GitHub release") a GPL build would place a real source-availability obligation on Mityu as a commercial distributor, for functionality it never uses.
**Decision:** Repoint Windows and Linux (x64 + arm64) FFmpeg downloads to a new GitHub Release, `aydogandagidir/mityu` tag `ffmpeg-deps-8.1-lgpl`, hosting unmodified re-uploads of the pinned `n8.1` **LGPL-only** static builds from `BtbN/FFmpeg-Builds` (a widely-used, actively-maintained community CI build of upstream FFmpeg, chosen over `evermeet.cx` for macOS parity-checking because BtbN explicitly labels and separately publishes LGPL-only artifacts; evermeet.cx's build also bundles libx264/libx265). Archive layout (`<name>/bin/ffmpeg[.exe]`) is byte-identical in shape to what `find_ffmpeg_in_extracted_dir` already searches for, so only the URL constant in `get_ffmpeg_url_for_target` changed — zero extraction-logic changes. Using the LGPLv3 build avoids the GPL-only codec/build terms, but it does **not** eliminate redistribution duties: the release still needs the applicable notices/license, corresponding source for the exact build (including its enabled LGPL dependencies), and reproducible build/source-offer material as required by the distribution model. **macOS (Intel + Apple Silicon) is intentionally NOT changed by this ADR** — no equivalently-licensed LGPL-only static macOS build was identified in this pass; those two targets still resolve to the original Zackriya-mirrored URL pending a separate fix (own follow-up, not blocking this one).
**Verification performed vs. NOT performed (read this before shipping):** Checked *without executing anything*: `tar -tJf` archive listings confirming the expected `<name>/bin/ffmpeg` paths, `file` on the extracted Windows binary confirming a valid PE32+ executable, and the three re-uploaded GitHub assets' sizes matching the downloaded originals byte-for-byte. **NOT checked: the new binaries were never executed.** `ffmpeg -version` against the new download — the check that would actually prove the LGPL config (`--enable-gpl` absent) and that the binary runs at all — was blocked twice by this session's safety controls, correctly: first when the agent tried to run the extracted binary directly, then again when the agent cleared the local binary cache to force `build.rs` to re-download and run it. (The second attempt was, in effect, the same denied action by another route; the cache was restored and no further attempt made.) Note that a routine `cargo build` does **not** exercise the new URL at all: `ensure_ffmpeg_binary()` finds the cached `frontend/src-tauri/binaries/ffmpeg-x86_64-pc-windows-msvc.exe` — which still holds the OLD gyan.dev GPL build — passes `verify_ffmpeg_binary()` on it, and returns early. A build log line reading `✅ FFmpeg verification passed: ... 8.0.1-essentials_build-www.gyan.dev` therefore proves nothing about the new artifacts. **Action required before shipping a signed release (human sign-off needed):** delete the cached `frontend/src-tauri/binaries/ffmpeg-*` file, run one real `cargo build`, and confirm the fresh log line shows a `-version` banner *without* `--enable-gpl` and *without* `gyan.dev`. Until someone does that, the LGPL claim in this ADR rests on BtbN's published artifact labelling, not on observed output from the specific files now in our release.
**Consequences:** Resolves the binary-host provenance and GPL-only build problem for Windows+Linux, and removes their runtime dependency on Meetily's servers, but the FFmpeg distribution gate is not complete until the exact LGPLv3 corresponding-source/build-script/notices bundle is durably published beside the binary. Remaining open, tracked in `docs/GA_READINESS.md`: (1) that compliance bundle; (2) macOS needs its own approved binary/source path and hardware verification, or a deliberate decision to accept GPL there with the corresponding obligations; (3) these binaries have no automatic update mechanism if `n8.1` is superseded — matches the previous pinned-tag pattern, deliberately, for build reproducibility, but means a human must re-mirror and refresh the compliance bundle for every future FFmpeg bump. The Windows execution test was subsequently completed and is recorded in the dated amendment/evidence above.
**Status:** Accepted (2026-07-07).

## ADR-0022 — The workspace `[patch.crates-io]` was never applied: cpal's macOS fix restored, esaxx-rs pin dropped, system-audio platform claims corrected
**Context:** Auditing the About-screen claim "Works everywhere — Google Meet, Zoom, Teams — online or offline" (`About.tsx:120-121`, `README.md:43`) surfaced a silent build-configuration defect plus three factual errors in our own docs.
1. **The patch block was inert.** `frontend/src-tauri/Cargo.toml` declared `[patch.crates-io]` for `cpal` and `esaxx-rs`, but src-tauri is a **non-root member** of the root workspace, and Cargo honors `[patch]` only in the workspace-root manifest (root `Cargo.toml` had none). Cargo says so out loud: `cargo tree -p cpal` printed `warning: patch for the non root package will be ignored` and resolved `cpal v0.15.3` from `registry+https://github.com/rust-lang/crates.io-index` (checksum, no git source) in `Cargo.lock`. Both pins had been dead for the life of the fork.
2. **Windows never depended on that patch.** Released cpal 0.15.3 already implements WASAPI loopback: `src/host/wasapi/device.rs:568-570` ORs in `AUDCLNT_STREAMFLAGS_LOOPBACK` whenever `data_flow() == eRender`, documented at `src/host/wasapi/mod.rs:18-20` ("If you use a WASAPI output device as an input device it will transparently enable loopback mode"). That is exactly what `audio/devices/platform/windows.rs:196-251` (resolve an output endpoint) plus `audio/stream.rs:272` (`build_input_stream` on it) do. This ADR's author first concluded the opposite — that the ignored patch broke Windows system audio — and was **wrong**; the claim was disproven by reading the vendored crate source before any code was changed. Recorded because the wrong version is the intuitive one.
3. **The real cost was macOS.** Pinned rev `51c3b43` is `RustAudio/cpal#946` "Fix macos non-default audio output" (2025-02-16), a **single-file** diff to `src/host/coreaudio/macos/mod.rs`: `supported_configs()`/`default_config()` hardcoded `audio_unit_from_device(self, /*input=*/true)` even when querying `kAudioObjectPropertyScopeOutput`, so config resolution is wrong for a **non-default output device**. That is the path `audio/devices/configuration.rs` takes for macOS system capture, and precisely the Bluetooth-speaker-as-system-output scenario `audio/devices/fallback.rs:112-126` and `BLUETOOTH_PLAYBACK_NOTICE.md` fight with. The crate version at that rev is still `0.15.3`, so `[patch]` applies cleanly.
4. **The esaxx-rs pin is unresolvable.** `github.com/thewh1teagle/esaxx-rs` returns "Repository not found" (`git ls-remote`; a control repo resolves fine). Relocating the block wholesale would have broken the build.
5. **"BlackHole" is doc fiction.** `CLAUDE.md` §4, `docs/SETUP.md:13`, ADR-0013's context line, and two `.claude/` prompts all state that macOS system capture "needs a virtual device (BlackHole)". It does not: the default backend is ScreenCaptureKit (`audio/capture/backend_config.rs:76`) with a Core Audio tap alternative (`audio/capture/core_audio.rs`, cidre). BlackHole appears only as a *pattern* — classified as a virtual device and treated as wired (`audio/device_detection.rs:177-178`), and explicitly **excluded** when picking a built-in output (`audio/devices/speakers.rs:100-105`).
6. **Linux system-audio capture is broken while deb+appimage ship.** `tauri.conf.json:83-89` lists `deb`/`appimage`. But `audio/devices/platform/linux.rs:18` queries the **ALSA** host for names containing `"monitor"` (a PulseAudio/PipeWire concept ALSA does not surface) and registers them as `"{name} (System Audio)"`, while `AudioDevice::from_name` (`audio/devices/configuration.rs:66-88`) *hard-errors* on any name not ending in `(input)`/`(output)`, and `configuration.rs:155-166` matches raw cpal names exactly — the suffixed name can never round-trip. The auto path fails too: `speakers.rs:38-45` returns the ALSA **output** device, which `configuration.rs` then hunts for among ALSA **input** devices. Separately, `audio/capture/system.rs:99-103` still `bail!`s "System audio capture not yet implemented for this platform" on non-macOS; it is reachable only through `start_system_audio_capture_command` (registered `lib.rs:745`, invoked by the UI **zero** times), and `audio/system_audio_stream.rs` has no callers at all.
**Decision:** (a) Move `[patch.crates-io]` to the **root** `Cargo.toml`, carrying **cpal only**, rationale inline; leave a "do not re-add it here" note where the block used to be. (b) **Drop** the esaxx-rs pin — the target repo is gone and `esaxx-rs 0.1.10` from crates.io builds on the MSVC toolchain we ship (the existing CUDA build proves it). (c) Correct the product copy rather than the platform matrix: the About card becomes "Any meeting app"; it and the README name the supported platforms (macOS + Windows) and mark **Linux experimental**, keeping the honest mechanism sentence ("captures system audio … not a bot that joins your call", per ADR-0018). ## ADR-0023 — Licensing & trial: Polar.sh (merchant of record) + client-side 14-day trial, with local-first guardrails

**Context:** The landing page sells Trial (14-day) / Pro ($79 one-time, 2 devices) / Business ($59/user/yr), but the binary contains zero enforcement: no payment link, no license concept, no trial clock. Any mechanism must not violate the constitution: local-first (§0.1 — the core path must work with no network), no plaintext secrets in SQLite (§7), no content to third parties (§10). Provider comparison (2026-07-11, owner decision): **Stripe** does not accept Türkiye-registered businesses; **PayPal** left Türkiye; **Gumroad** has no TR payout (and its name is banned from every user-facing surface by owner directive); **LemonSqueezy** is mid-migration to Stripe Managed Payments with TR payout unconfirmed; **Paddle** verifiably pays TR sellers but has no native license keys (would force a Keygen-class dependency or a self-hosted license server) and charges a $15 flat SWIFT fee per payout; **iyzico / PayTR** are gateways, not MoR — we would owe worldwide buyer-side VAT/sales-tax compliance plus the TR 1% e-commerce withholding, and they bring no license infrastructure (kept as a possible future TR-local channel in TRY with taksit). **Polar.sh** is a merchant of record (buyer-side tax is theirs), explicitly supports Türkiye-based sellers, is open source (polarsource/polar), and ships native license keys with activation limits, optional expiry, and a customer self-service deactivation portal. Fees: 5% + 50¢ (Starter tier for orgs created ≥ 2026-05-27), $15 per dispute; payout via Stripe Connect Express. For a TR seller the MoR model makes every sale a service export (KDV %0 + the 2026 "%100 kazanç indirimi" regime, CK 11257) — **to be confirmed with the accountant; this ADR is not tax advice.** Owner picked Polar.sh; launch version = 1.0.0.

**Decision:**
1. **Provider = Polar.sh** with hosted checkout: the landing page's buy buttons link to Polar checkout URLs. The app itself never touches payment data.
2. **Only Polar's public customer-portal endpoints are used** — they require no API secret, so nothing sensitive is baked into the binary: `POST api.polar.sh/v1/customer-portal/license-keys/activate` `{key, organization_id, label}` → 200 `{id, license_key{…}}` | 403 activation-limit | 404; `…/validate` `{key, organization_id, activation_id?}` → 200 `{status: granted|revoked|disabled, expires_at?, limit_activations, …}` | 404; `…/deactivate` `{key, organization_id, activation_id}` → 204. Sandbox host `sandbox-api.polar.sh` for tests/dev.
3. **Organization id via `option_env!("MITYU_POLAR_ORG_ID")`** (the ADR-0016 PostHog pattern): unset ⇒ the activation UI reports "licensing not configured" while trial mechanics run normally — the repo builds and runs before the Polar account exists; release builds inject the real id (GitHub secret, wired like `MITYU_POSTHOG_API_KEY`).
4. **Trial: client-side, 14 days, full-featured, no account, no card.** Anchor = first-launch timestamp stored twice — settings JSON (`licensingState`, per-workspace, the ADR-0015 `redactionConfig` pattern, **no schema migration**) and keychain entry `licensing:trial-anchor` — earliest wins, each heals the other if missing. Clock-rollback guard: a persisted high-water `last_seen_at`; effective now = max(system clock, high-water). **Honest-user stance, not DRM:** a client-side trial is bypassable by a determined user; accepted deliberately — the audience pays for updates, support and legitimacy, and the privacy promise (no phone-home) outranks enforcement strength.
5. **Expiry gates capture only — never data.** `TrialExpired`/`Revoked` blocks exactly two entry points: starting a new recording and importing audio. Opening the app, browsing/searching/exporting every existing meeting, playback, summaries of already-captured content, and settings remain available forever. This extends ADR-0014's "never lock the user out of their own meetings."
6. **Activation flow:** user pastes the key (Settings → License, or the paywall dialog) → `activate` with a stable random pseudonymous `label` (never the hostname; stored as `licensing:device-label` when the OS credential store is available) → persist key + activation_id in the **keychain only** (`licensing:key`, `licensing:activation-id`; §7 — never SQLite). Non-secret display state (masked key, plan, expires_at) is cached in the settings JSON.
7. **Validation: lazy, rate-limited, fail-open offline.** Re-validate at most once per 7 days, fire-and-forget in the background after status reads (never blocking a status read or startup on the network). Transport errors ⇒ remain `Licensed` (local-first). Explicit negatives act: `revoked`/`disabled` or past `expires_at` ⇒ `Revoked`/expired state with a re-activation path; 404 with our activation_id ⇒ the seat was freed via Polar's portal ⇒ clear local license and fall back to the trial state machine. Requests carry ids only — never content, never telemetry (§10).
8. **Deactivate** (Settings) calls the endpoint, then clears the keychain entries — frees the seat under the 2-device activation limit; Polar's customer portal offers the same self-service without us.
9. **States** (single source of truth in the Rust `licensing/` module): `Trial{days_left}` · `TrialExpired` · `Licensed{plan, expires_at?}` · `Revoked{reason}`. The UI consumes `get_licensing_status`; gated commands fail with a machine-readable `LICENSE_REQUIRED` error the UI maps to the paywall.
10. **Business ($59/user/yr) later:** identical key mechanics — `expires_at` is honored from day one — so post-launch it only needs the Polar product/benefit and copy.

**Consequences:** + fastest possible launch (no license server of ours), buyer-side global tax at the MoR, the 2-device promise enforced by Polar's activation limit, seat swaps self-service; − one new outbound endpoint (`api.polar.sh`) to document in `SECURITY_PRIVACY.md` (user-triggered activate/deactivate plus ≤1/7-day validate; ids only), *new* activations depend on Polar uptime (running installs don't), the client-side trial is bypassable (accepted above), the org id is public by design (it is in every checkout URL anyway). Gates live at the **command layer** — zero edits inside capture internals (§4). Implementation on `feat/licensing`: Rust `licensing/` module + 3 commands + 2 gates; frontend `licensingService` + trial banner + License settings section + paywall dialog; tests on both sides.

**Status:** Accepted (2026-07-11 — owner decisions: provider = Polar.sh, launch version = 1.0.0). Implemented on `feat/licensing`.

**Amendment (2026-07-11, at implementation):** The per-workspace `licensingState` JSON blob physically lives in the pre-existing — and otherwise dead — upstream `licensing` table, one marker row per workspace (`license_key = 'licensingState:<ws>'`, `signature_hash = 'licensingState:v1'`, JSON in `encrypted_key`), because the fixed-column `settings` table cannot host a new blob without the schema migration this ADR forbids; legacy upstream RSA rows are ignored via the marker filter, and the table is SQLCipher-encrypted at rest like the rest of the DB. The trial anchor is minted lazily at the first status read (the UI reads status at startup, so this coincides with first launch; pre-DB onboarding reads serve a keychain-only status that heals into the blob after DB init). Retranscription of already-captured audio is deliberately NOT gated (§5 — data is never hostage); the two gates are recording start and audio import, at the command layer only.

**Amendment (2026-07-15, privacy hardening):** Polar activation labels no longer contain the operating-system hostname. Mityu generates `mityu-<random UUID>` and stores it in the OS credential store for stable portal display; when that store is unavailable, the one-time random label is still used and activation never falls back to a hostname. This is a data-minimization change and does not alter seat validation semantics.

## ADR-0024 — Product Intelligence starts with local, source-resolvable Evidence Search

**Context:** The owner requested Mityu's product-intelligence layer while A5 real-audio validation and the C8 pilot gate remain open. The legacy search path uses unranked `LIKE`, returns meeting-level matches without a stable segment anchor, and can mix transcript results with legacy summary JSON that has no reliable HITL approval boundary. Starting with generative “Ask Mityu” would therefore lack a deterministic retrieval baseline and could present unreviewed AI text as authoritative.

**Decision:** The first Product Intelligence slice is Ranked Evidence Search v1. Migration `20260714000000_add_transcript_evidence_search_fts` creates an encrypted local FTS5 derived index plus a stable transcript-id routing map; it backfills existing rows and maintains the index across transcript and meeting lifecycle changes. The trusted `api_search_evidence` command accepts only a bounded literal token/prefix query, ranks with BM25, returns at most the best active segment per meeting, and joins every result back to active `transcripts` and `meetings` scoped by `AuthContext.tenant_id`. Every result includes a resolvable `source_chunk_id`, timestamp and original-text snippet. Raw rank is internal ordering metadata, not confidence. Query and snippet content are prohibited from logs and analytics. Legacy and unapproved summary text is excluded.

The FTS index remains a local-only derivative inside SQLCipher: it has no sync entity or wire representation and the multi-tenant server must not reuse it. The previous `api_search_transcripts` command remains for compatibility, but its content-bearing logging is removed and product UI uses the evidence command with debounce, stale-response suppression and exact-segment deep links.

**Consequences:** Mityu gains an offline deterministic retrieval foundation for later citation-first intelligence without an LLM or network dependency. Transcript text is duplicated inside the encrypted database, increasing disk use. ADR-0026 now defines and implements the app-controlled FTS/WAL/free-page cleanup boundary; it deliberately does not promise forensic erasure from storage layers or copies outside Mityu's control. The migration advances SQLx's forward-only ledger, so application downgrade after opening the database is unsupported. This quality-independent slice may land before A5 by owner direction, but does not complete A5 or C8.

**Status:** Accepted (2026-07-14; implementation authorized by owner, release claims remain A5/C8-gated).

## ADR-0025 — Approved Action Center is an approval projection, not a task tracker

**Context:** Evidence Search provides trustworthy retrieval, but users still have to open meetings individually to find reviewed follow-ups. `action_items.status` (`draft | approved | edited | rejected`) is a HITL review state, not real-world work progress. Treating `edited` as approved, adding a completion checkbox without a separate work-state contract, or interpreting free-text `due` values as deadlines would collapse distinct meanings. Repository review also found that producer-supplied status and inactive evidence needed stronger write-time enforcement before a cross-meeting view could claim “human approved.”

**Decision:** Product Intelligence slice 2 is the fully local, read-only `/actions` Approved Action Center. It returns only active `action_items.status = 'approved'` rows whose active meeting and active same-meeting transcript source all belong to the caller's tenant. Item approval is independent of whole-summary approval; `draft`, `edited` and `rejected` are excluded. Results preserve deterministic backend order and expose bounded pagination, source metadata, assignee and verbatim free-text due values. V1 adds no work-progress field, completion mutation, overdue inference, reminder, analytics content or external action.

The write boundary is hardened with mandatory Draft persistence for generated summary blocks and action items, removal of forged edit provenance, active meeting/source checks repeated after obtaining the SQLite writer transaction, and status+revision compare-and-swap updates. Approval additionally requires an active source in the same meeting and tenant. The Action Center UI reuses the exact transcript-segment jump/highlight path and describes items as AI-extracted and human-approved.

**Consequences:** Users gain an evidence-linked place for reviewed commitments without exposing drafts or inventing task semantics. A future task workflow requires a separate additive work-state contract. Offset pagination is intentionally visible and bounded; multi-writer sync may later require a cursor. The Home Dashboard's existing broader `list_open` review surface remains separate from the approved-only Action Center.

**Release-line amendment (2026-07-14):** implementation was rebased onto published `v1.0.3`. The owner subsequently approved `v1.0.4` as the release candidate for this work. Package, Tauri, Rust, lockfile and browser surfaces must remain synchronized at `1.0.4`; the published `v1.0.3` tag remains immutable.

**Status:** Accepted (2026-07-14; implementation authorized by owner, release claims remain A5/C8-gated).

## ADR-0026 — Verifiable local deletion covers Mityu-managed stores, not every physical replica

**Context:** Before this decision, a meeting hard-delete removed tenant-scoped SQLite rows and FTS routing/index entries logically, but SQLite ordinary pages, FTS5 merge segments and WAL have different remanence behavior. Recording folders and the WebView IndexedDB recovery cache were separate stores. Claiming physical or forensic erasure from only SQL row deletion would therefore be false. At the same time, recursively deleting an arbitrary `folder_path` would risk destroying user files or following a link outside Mityu's recording root. SSD wear-leveling, copy-on-write filesystems, snapshots, backups, swap, exports and browser/WebView storage also sit below or outside the app's authority.

**Decision:** Migration `20260714010000_enable_verifiable_local_deletion` persists FTS5 `secure-delete=1` and creates `local_privacy_maintenance`, a singleton content-free retry marker. Every pool connection enables SQLite core `PRAGMA secure_delete=ON`; the exact deletion connection verifies both controls before changing data. The tenant-scoped database delete and `required = 1` marker update commit atomically. That delete runs on a disposable `close_on_drop` connection with SQLite FK cascades disabled, explicitly deletes every child row with `workspace_id = AuthContext.tenant_id`, and never queries a foreign workspace; a malformed foreign child is left untouched instead of being discovered or cascaded away. A successful maintenance cycle then runs FTS `optimize`, requires a complete `wal_checkpoint(TRUNCATE)`, runs `VACUUM`, requires another complete WAL truncate and `freelist_count = 0`, records completion, and requires a final marker checkpoint. The marker clears only after success; startup reruns a pending cycle, so a crash after the logical commit cannot silently skip compaction.

Before the database commit, Mityu may scrub/unlink only its known recording, metadata, transcript and checkpoint artifacts in the meeting folder. New folders live below a collision-free hex-encoded workspace namespace and `metadata.json` carries the trusted `workspace_id` resolved in Rust. Erasure validates that ownership marker before touching files; a foreign marker fails closed without a database lookup. Legacy folders with a missing marker/field are accepted only for the implicit `local` workspace. The target and configured/default recording roots are canonicalized; outside-root targets, a root itself, same-workspace duplicate folder references and unsupported paths fail closed. Symlinks are unlinked but never followed. Unknown top-level user entries are retained, and the meeting directory is removed only when empty. This ordering leaves database data intact and retryable if app-managed artifact removal fails. The WebView recovery cache is logically deleted immediately after a recovered meeting is saved to SQLite, retried at startup for older/interrupted saves, and purged on explicit meeting deletion.

The automated `secure_local_deletion.rs` integration test plants a unique sentinel in domain rows, FTS, WAL-capable database storage, audio, metadata, transcript JSON and checkpoints. It proves a foreign delete is a no-op, a caller-scoped delete leaves a malformed foreign child untouched, and a same-workspace duplicate folder reference fails closed; unit coverage proves foreign ownership markers fail before artifact erasure and legacy unmarked folders are local-only. After the owner deletion and maintenance cycle it verifies all relevant caller-owned SQL/FTS rows are gone, FTS and core secure-delete are enabled, the free list is empty, WAL is absent or truncated, the sentinel is absent from SQLite/WAL artifacts and Mityu-managed files, and an unknown user file survives. Product deletion copy must always state that these checks establish the Mityu-controlled application boundary—not guaranteed physical erasure from SSD wear-leveling, COW layers, snapshots, backups, exports, swap or WebView/browser remnants.

**Consequences:** C6a's implemented/tested deletion-semantics gate is closed for v1.0.4, but A5, C8, legal, signing, updater-canary and FFmpeg source-compliance gates remain independent. Deletion can be slower because it compacts the whole local database, and it can return an error while WAL is busy; the content-free marker preserves a startup retry. Unknown user-added entries are intentionally not deleted. The migration is client-only and adds no sync entity or meeting content, but application downgrade is unsupported: FTS5 secure-delete requires SQLite 3.42+ and Mityu's bundled SQLCipher/SQLite is 3.45.3.

**Status:** Accepted and implemented (2026-07-14; C6a closed, release remains A5/C8-gated).

## ADR-0029 — v1.0.4 ships updater-signed only; Windows Authenticode deferred (owner decision)

**Context:** The v1.0.4 hardened release workflow was authored to require Windows Authenticode code signing via DigiCert KeyLocker (five `SM_*` secrets) *in addition to* the Ed25519 Tauri updater signature, behind a fail-closed preflight that refuses to build a release unless all seven signing secrets are present. A read-only investigation on 2026-07-15 established that **no `SM_*` DigiCert secret has ever existed in this repository** — the account is a personal user (not an org, so no org secrets), the `Production` environment holds zero secrets, and repository scope holds only `TAURI_SIGNING_PRIVATE_KEY` + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Therefore v1.0.0–v1.0.3 were **never Authenticode-signed**; every prior release shipped with only the Ed25519 updater signature (the `.sig` assets, which are present on all four releases) and consequently triggers the Windows SmartScreen "unknown publisher" prompt. DigiCert Authenticode was thus a *new* v1.0.4 hardening that the fail-closed preflight made mandatory for the first time. The product owner (2026-07-15, via explicit decision) chose to ship v1.0.4 the same way as the already-published v1.0.x line — updater-signed only, no Authenticode — rather than acquire and provision a code-signing certificate now.

**Decision:** For v1.0.4, make Windows Authenticode **optional and off**, while keeping the Tauri updater signature **mandatory and fail-closed** so the v1.0.3 → v1.0.4 auto-update chain is preserved. Three surgical release-pipeline edits:
1. `release.yml` "Validate updater signing configuration" preflight now requires only `TAURI_SIGNING_PRIVATE_KEY` + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the five `SM_*` inputs are no longer required.
2. `release.yml` dispatches `build-windows` with `sign-binaries: false`.
3. `build.yml` "Validate release-mode contract" still requires a release id in production mode but no longer mandates platform signing.

No new secret and no updater-password recovery are needed: the updater key + password already live as **repository** secrets (they signed v1.0.3) and are readable by the `Production`-environment `create-release`/`build` jobs (an environment job can read repository secrets). **Consequences:** v1.0.4 installers carry no Windows publisher identity, so users continue to see the SmartScreen "Windows protected your PC / unknown publisher" prompt exactly as on v1.0.0–v1.0.3 (More info → Run anyway). Product, release and landing copy must not claim a verified publisher, Authenticode, or a "signed installer" in the publisher-identity sense; **"updater-signed" is the accurate claim.** This is a support/trust cost accepted for a paid product and should be revisited. Re-enabling Authenticode later (the deferred "option A") requires acquiring a code-signing certificate (OV/EV, identity validation, a DigiCert KeyLocker account), provisioning the five `SM_*` secrets in `Production`, and reverting these three edits (set `sign-binaries: true`, restore the `SM_*` preflight requirement, restore the production platform-signing requirement). The `Production` reviewer gate, `main`-only deployment policy, exact-SHA protected CI, legal/commercial sign-off, legacy-lead disposition, updater-artifact inspection, and the post-publish v1.0.3 updater canary are all unchanged and remain fail-closed. Migrating the updater secrets from repository scope to the `Production` environment (the RELEASE "Production key governance" item) is deferred together with Authenticode: it is not required for this release because environment jobs can read repository secrets, and it still needs the original updater-key password, which is unavailable locally.

**Status:** Accepted (2026-07-15; explicit product-owner signing-scope decision for v1.0.4). Updater chain preserved; Authenticode deferred, not waived.

## ADR-0030 — Local learning: the HITL correction signal becomes plain-language rules, not weights

**Context:** The owner asked (2026-07-16) whether to build a self-improving / learning agent system into Mityu. Auditing the code first changed the answer twice, so both wrong turns are recorded — in each case the intuitive version is the wrong one.

1. **The capture half already exists and is good.** Every AI-drafted block keeps `original_content` beside the human's `content` (`summaries.sections` JSON), every action item keeps `original_text` beside `text`, with a `draft|approved|edited|rejected` state machine (`summary_draft.rs:204-217`), 11 Tauri commands (`lib.rs:712-722`), and source-evidence anchors re-resolved at approve time (`summary_draft.rs:643-656`). **But no generation path has ever read it**: `original_content`/`original_text` appear only in the repositories that write them, the type definitions, the UI that displays them, and tests. The signal is captured and inert. The gap is consumption, not capture.
2. **Three defects make today's signal unusable as-is.** (a) `upsert_draft` rewrites `sections` **wholesale** (`summary_draft.rs:323-338`), so regenerating a summary destroys every prior `original_content` — the signal evaporates exactly when the user iterates most. (b) A rejection records `status='rejected'` and no rationale: "this was wrong" is not teachable, "wrong because X" is. (c) `original_content` is set only on the *first* edit (`summary_draft.rs:569-571`).
3. **"N=0 users ⇒ nothing to learn" was wrong.** That reasons about *aggregate* learning. Local-first learning is **per-user**: customer #1 learns from customer #1's own corrections — "1 user × repetition", not "many users". It also cannot be retrofitted onto usage that was never recorded, so the system must ship **active**, or every early customer's first month is lost.
4. **"A self-modifying policy violates §0.5 HITL" was mostly wrong, and the code says why.** `upsert_draft` **forces** `status='draft'` (`summary_draft.rs:324,347`) and `approve_summary` requires every non-rejected block approved (`:591-678`). A learned rule can therefore only change the shape of a **draft**; a human still approves every block. The output gate bounds the blast radius. What survives from that objection is not safety but **reproducibility**: EU AI Act Art.50 and the dispute-evidence claim require knowing which rules shaped a given summary.
5. **"We can't measure it" was mislocated.** It was tied to Phase-0, which is at **0 clips** — and which measures WER/CER/term-recall, i.e. **not summary quality at all** (ADR-0019 gates summary quality on a gate that does not measure it; that inconsistency is real and independent of this ADR). But the learning objective needs **no labeled data**: *correction burden* — normalized Levenshtein(`original_content` ↔ `content`) plus rejected-block rate — is computable from rows the app already writes.
6. **Two walls do not move.** **Weights** (fine-tune/LoRA/RL): KVKK/GDPR erasure is not satisfiable against a trained model — "machine unlearning" is a research topic, not a product feature — and under BYOK we do not own the model anyway. **Cross-tenant / cloud aggregation**: violates §0.1 and §10. Both are rejected on legal/architectural grounds, not preference.

**Decision:**
1. **Learning is data, not weights.** Learned state = plain-language rules in SQLite, retrieved and injected into the prompt at generation. Deterministic, inspectable, and erasable with one `DELETE`.
2. **`correction_events`** — a new **append-only** table (append-only enforced at the repository layer; SQLite cannot express it without a trigger, and a trigger would fight the CASCADE in §11). One row per human HITL action (`edit`/`reject`/`approve`/`restore`) carrying the draft text, the human text, and the generation context (`template_id`, `model`, `block_type`, `section_title`). It is a **separate table specifically to survive `upsert_draft`'s wholesale rewrite** — that is the fix for defect 2(a), not a convenience.
3. **`reason`** on correction events; the reject UI collects it, optionally, never blocking the reject. Fixes defect 2(b).
4. **`learned_rules`** — derived rules. `status`: `proposed|active|dismissed`. `origin`: `mined_deterministic|mined_llm|user_authored`. `rule_text` is **plain language**, user-editable and user-deletable. `evidence` = JSON id list of the correction events that produced it.
5. **`summaries.applied_rules`** — a snapshot of `{rule_id, rule_text, scope}` written at generation time. **The text, not just the ids**, because rules are editable: an id alone cannot reproduce a six-month-old summary. This is the Art.50 requirement and the precondition for §7.
6. **Injection at `build_structured_system_prompt`** (`summary/structured.rs:313-343`), deterministic ordering by rule id. **The same seam `custom_prompt` needs** — it is currently threaded to `api_process_transcript` but consumed only *after* the structured block ends (`service.rs:607/613/660`), so with `structuredSummaries` defaulting **true** the user's custom prompt is **silently dead on the default path** today. Fixing that is free once this seam exists, and the manual knob must work before the automatic one is credible.
7. **Auto-activation is permitted, behind `learningConfig.autoActivate` + `autoActivateMinSupport` (default 3)** — permitted *only* because §4's output gate bounds it and §5 makes it reproducible. Mined rules are otherwise born `proposed`. `user_authored` rules are born `active`: the user writing the rule *is* the approval.
8. **Miners: deterministic first** (term substitution, section rejection, length preference) — free, and the most legible to the user, so they carry the product story. **LLM miner** via the existing BYOK provider for subtler patterns: **no new privacy surface** (the transcript already goes to that provider for summarization), and Ollama users stay fully local. Both emit `ProposedRule` = data with no apply method, per **ADR-0013**.
9. **Objective = correction burden**, computed from `correction_events`, surfaced in-product ("Mityu learned 12 rules from your 47 corrections; your correction burden dropped 31%"). `eval-harness/src/metrics.rs` already holds Levenshtein + Turkish-aware normalization, and `eval-harness` already depends on the core crate (`eval-harness/Cargo.toml:28`), so moving that code **into** the core is a dependency-correct one-way refactor both sides consume. **This unblocks measuring the learning system without the Phase-0 clips.**
10. **Erasure asymmetry (the whole argument for data-over-weights).** `correction_events.meeting_id` **CASCADEs**: deleting a meeting deletes the corrections derived from it, so "delete my data" stays a real `DELETE` with no residue. The `learned_rules` derived from them **survive deliberately** — a rule is an abstraction the human approved ("call it 'takip'"), carries no transcript text, and is independently deletable. Evidence id lists may therefore dangle; readers **must** degrade to "kanıt silindi", never error.
11. **Both new tables are LOCAL-ONLY by policy** and get **no `SyncEntity`** in this ADR. `correction_events` stores raw meeting content (the draft and the human's rewrite of it), making it the most sensitive table in the schema after `transcripts`. Phase-2 sync policy for corrections and for rules is explicitly **out of scope and owed**.

**Verification performed vs. NOT performed (read this before relying on any of it):** *Performed.* Every code claim above was read at `HEAD` (`0a503be`, `main`) and is cited to file:line. The four new identifiers (`correction_events`, `learned_rules`, `applied_rules`, `learningConfig`) were confirmed absent from **every** schema lineage this app can encounter — all 13 pre-existing files in `migrations/` and the legacy `backend/app/db.py` import path — which is what makes the unguarded `ADD COLUMN`s safe by construction. **The full 14-file migration chain was executed in order against a scratch SQLite database and applied clean**; `PRAGMA table_info` confirms both new tables with the intended columns/defaults, `summaries.applied_rules` and `settings.learningConfig` present, all five indexes created, and `PRAGMA foreign_key_list(correction_events)` reporting `-> meetings on_delete=CASCADE`. **§10's erasure asymmetry was proven empirically, not asserted:** with `PRAGMA foreign_keys=ON`, inserting a meeting + 2 correction events + 1 derived rule and then `DELETE FROM meetings` took `correction_events` 2 → 0 (meeting content is really gone) while the `learned_rule` survived with its `evidence` list `["e1","e2"]` now **dangling** — which is precisely why readers must degrade to "kanıt silindi" rather than error — and the rule itself was then removed by a single `DELETE`. That contrast *is* the data-over-weights argument, now demonstrated. **The app's real migration path is green:** `cargo test -p mityu --test migration_workspace_sync` → **4 passed, 0 failed** with this file in the directory, i.e. through `sqlx::migrate!` itself, not a hand-rolled runner. Two of those four are the ones that matter here: `rerunning_full_migrator_is_a_noop` demonstrates the ledger guarantee that the non-idempotent `ALTER`s below depend on, and `populated_db_upgrade_backfills_and_preserves_data` demonstrates an existing populated database upgrading across this migration without data loss. *NOT performed, at the time this paragraph was written (A1).* **No Rust or TypeScript existed yet** — §2–§9 unbuilt; no clippy, no tsc, no smoke test. The schema is therefore **unproven against the repository layer** — in particular, whether `subject_id` can stay polymorphic across summary blocks (ids inside JSON) and action items (real rows) with no FK, following the `source_chunk_id` precedent (`20260706000000` header), is a design claim only A2 can confirm. **The two `ALTER`s are NOT SQL-idempotent** (SQLite has no `ADD COLUMN IF NOT EXISTS`): a second execution of this file would fail on duplicate columns. Treat this ADR as an accepted *decision* with a *validated schema* and an *unbuilt* implementation.

**Consequences:** **+** The correction signal becomes durable (survives regenerate), minable, and measurable with an objective that needs no golden dataset and no Phase-0 clips; `custom_prompt` gets fixed as a side effect of the injection seam; the differentiator is demoable from customer #1 because it is per-user; the rules screen doubles as the KVKK/AI-Act defence (opaque "our AI learns you" is exactly what cannot be defended). **−** One new table pair, one column on `summaries`, one on `settings`; `correction_events` holds meeting content (SQLCipher-encrypted at rest like the rest of the DB, LOCAL-ONLY, cascading on meeting delete); the LLM miner spends BYOK tokens (on-demand, user-triggered, never background); rule state is per-workspace, so Phase-2 must decide whether rules sync — recorded as owed above. **Scope note:** this ADR touches the summary/prompt path and the DB schema; per §10 it must not be combined with any audio-pipeline change.

1. **There are TWO system-prompt builders, not one.** `build_windowed_system_prompt` serves the windowed mode — which is what long meetings, every BuiltInAI user, and Ollama-over-threshold get. *Two design corrections this phase forced, both worth the words:*
1. **`[]` and `NULL` are different claims, and A1 had them muddled.** The A1 migration comment said NULL meant "before this migration, **or** with no active rules", while the A1 test comment said NULL "must stay distinguishable from an empty snapshot" — those contradict. Settled: **`'[]'` = the learning system ran for this summary and applied nothing ("no, and we checked"); `NULL` = nothing was ever recorded (a pre-migration row, the first-run sample, which inserts its own row directly, or a summary from the legacy markdown path — "we do not know")**. An audit must be able to tell *no* from *don't know*, so the read path keeps the `Option` all the way out, and the column keeps **no DEFAULT**: a `DEFAULT '[]'` would silently promote every pre-existing row from "unknown" to "audited, nothing applied" — a claim the migration is in no position to make. The A1 migration comment was corrected in place; this is legitimate precisely because that file is **untracked and has never been applied to any real database** (§6 forbids editing *applied* migrations).
2. **`scope` is snapshotted as the raw token, not `RuleScope`.** An archival record must stay readable if the scope vocabulary later grows; parsing an old record against today's enum turns an archive into a liability.

*Decisions worth their words:*
1. **`create` COMPUTES the birth status; it does not accept one.** Otherwise any future caller could mint an `Active` rule by asking, and auto-activation would stop being something the *user's policy* controls.
2. **The status machine has no arc back to `Proposed`.** Once the human has answered, the answer stands until they change it; re-proposing a settled question is the nagging the machine exists to prevent.
3. **Dismiss ≠ delete, deliberately.** `Dismissed` keeps the row — the refusal is ON THE RECORD, which is what lets the miner tell "never proposed" from "proposed and refused". `soft_delete` removes it from the list and carries no memory of refusal, so **a deleted rule can be re-learned** if the behaviour repeats. That is the system working, not a bug — but §9's copy must say so in those words, or users will read Delete as "never again".
4. **The corrupt-config fallback is `disabled()`, not `default()`.** `get_learning_config` distinguishes ABSENT (no preference was ever expressed → the product default, auto-activation on) from CORRUPT (the user *had* preferences we cannot read → everything off). Falling back to the default on a corrupt blob would silently re-enable auto-activation for someone who deliberately switched it off. This is the same principle as the redaction repository's "never silently enable redaction from a bad blob"; the fallback differs only because redaction's safe state happens to equal its default and learning's does not. Every config field carries a serde default, so an older/partial blob fills gaps from the product default instead of tripping the corrupt path — which keeps true corruption rare enough for `disabled()` to be as blunt as it is.
5. **`auto_activate` defaults ON, `llm_miner_enabled` defaults OFF.** The first because §7's three bounds hold (output HITL gate, §5 snapshot, §9 visibility) and the owner's directive is that customers must SEE the difference. The second not for privacy — the transcript already goes to that provider — but because the LLM miner **spends the user's own API budget**, and enabling a paid background process on someone's behalf is not a default anyone gets to choose for them.
6. **A failed rule/config read degrades to no guidance; it never fails the summary.** The user asked for a summary, not for a learning system.

## ADR-0031 — A5 gate thresholds are locked before measurement, and term recall is gated per domain

**Context:** `docs/PHASE0_VALIDATION.md` §4 offers a *suggested starting bar* for the A5 transcription gate and explicitly instructs that "the agreed numbers" be recorded in `DECISIONS.md`. They never were. A5 has therefore been carrying a gate with no committed pass/fail line — an unrecorded threshold is not a gate, because the bar can move after the numbers land. Separately, the product owner decided (2026-07-26) to evaluate **two domains** in one run — 5 legal + 5 intralogistics clips — which changes what the jargon threshold even means: the `jargon` bucket now mixes two vocabularies whose recall figures are not comparable.

Both facts were surfaced while authoring `docs/A5_SPRINT.md`, the execution runbook for A5. The eval set itself remains `0/5` in every bucket; the only blocker is human evidence collection, not code.

**Decision:**

1. **The §4 starting bar is adopted verbatim and locked, before any measurement runs.** GO (full scope, field included) requires **median strict WER ≤ 0.15 (quiet)** *and* **≤ 0.25 (field)** *and* **jargon term recall ≥ 0.80**. CONDITIONAL(meeting-room) = quiet passes, field does not. NO-GO = quiet is unusable after vocabulary tuning. These are the constants already compiled into `eval-harness/src/report.rs` (`GO_QUIET_WER`, `GO_FIELD_WER`, `GO_TERM_RECALL`); this ADR is what makes them the *agreed* numbers rather than a default.
2. **Term recall is gated per domain vocabulary, not per bucket.** GO requires **every** jargon domain to clear 0.80 independently. A single blended bucket median is explicitly rejected as the gate number: with legal at 0.60 and intralogistics at 1.00 the merged median lands on exactly 0.80 and reads PASS while one domain plainly fails. If one domain passes and another does not, the result is **not** GO — CONDITIONAL may be considered for the passing domain and the failing domain remains open evidence debt.
3. **Turkish CER (diacritic-folded) is reported as a secondary metric and does not relax the bar.** Turkish is agglutinative, so word-level WER runs structurally higher than in English; CER makes that visible and informs the reading of a near-miss, but the thresholds above are not loosened on its account. Any future change to these numbers requires a new ADR — never an edit to this one after results are known.
4. **The verdict stays human.** The harness computes metrics and pre-fills the threshold table; it never writes GO/CONDITIONAL/NO-GO. `CLAUDE.md` §0.5 and the §4 protocol both require a human to sign the gate, and an AI agent may not substitute for the pilot reviewer.

**Consequences:** A5 now has a committed pass/fail line that predates its data, which is the only arrangement under which the gate constrains anything. The per-domain rule required harness work, delivered with this ADR (`eval-harness`): clips carry a domain vocabulary set (`eval/jargon.<set>.txt`, selected per clip by an `<id>.vocab.txt` sidecar, unknown names failing closed before a model loads); `Row.vocab_set` records which vocabulary scored each clip; `medians_by_domain` + `jargon_domains` land in `report.json`; and the Markdown threshold table emits one row per (config × jargon domain) with its own PASS/FAIL. A single-domain run renders as before. Cost: two domains mean 25 recordings rather than 20, and each `jl*` clip needs a one-line sidecar. Unchanged: the fail-closed ≥5-pairs-per-bucket gate, the human-corrected-reference requirement, the prohibition on public datasets as gate evidence, and ADR-0027's rule that A5 remains NOT EVALUATED — deferred for v1.0.4 publication only — until a human runs and signs it.

**Status:** Accepted (2026-07-26; product-owner threshold and two-domain decisions). Thresholds locked pre-measurement; A5 itself remains open and unevaluated.

## ADR-0032 — EU AI Act Art. 50 verification: the marking holds on every reachable path, and is now test-protected

**Context:** Art. 50 transparency obligations apply from **2 August 2026**. `docs/A5_SPRINT.md` §4 (Aşama 0.2) required a pre-deadline confirmation that the two things Mityu's documentation claims are actually true in the code: that the AI-generated marking cannot be suppressed, and that exported output carries a machine-readable marking. A claim in a comment is not a control; this ADR records the verification and what it changed.

**Verification result (2026-07-26, source-level audit):**

1. **Non-suppressible in-app marking — HOLDS on every reachable path.** With the default `structuredSummaries: true`, `DraftSummaryView` renders `ReviewRequiredBanner` in all four states (loading, error, empty, populated); it has no close control and no state that hides it. With the flag turned off, `SummaryPanel` derives `isLegacyUnverified = !!aiSummary && !structuredEnabled`, which is therefore *always* true when a summary exists, so `BlockNoteSummaryView` shows `LegacyUnverifiedBanner` and renders the content read-only with copy and export disabled. LLM-mined learning rules are labelled `Suggested by the model`.

It is embedded in all three export formats: PDF as XMP under `https://bluedev.dev/mityu/export-provenance/v1#`, DOCX in `description` + `keywords`, Markdown as YAML front matter. `buildVerifiedExportProvenance` throws (`ExportApprovalError` / `ExportSourceLinkError`) rather than emitting an unapproved or unlinked document, so the renderer fails closed.

It is dead code: `page-content.tsx` declares `const [summaryResponse] = useState<SummaryResponse | null>(null)` with no setter, so the value can never become non-null. Recorded here because the next reader will find the same block and must not "fix" it by wiring it up without adding a marking.

**Decision:** The verification stands as PASS for both claims, and the in-app marking is now protected by an executable test rather than by convention. `frontend/src/components/AISummary/DraftSummaryView.transparency.test.tsx` asserts the banner is present in all four states and contains no control that could dismiss it, querying it through its ARIA role and accessible name (wording, colour and icon are deliberately not pinned — the accessible marking is). The suite was proven to have teeth: removing the banner from a single branch turns exactly that case red.

This required the frontend's first component-test infrastructure. `environment: 'node'` stays the **default** — the new suite opts into jsdom with a per-file `@vitest-environment` docblock — so pure-logic tests keep their speed. Added dev dependencies: `jsdom`, `@testing-library/react`, `@testing-library/dom`. `oxc.jsx.runtime: 'automatic'` was required in `vitest.config.ts` because `tsconfig.json` sets `"jsx": "preserve"` for Next; note that this Vitest runs on Vite 8 / Rolldown, whose transformer is **oxc**, so an `esbuild.jsx` setting is silently ignored.

**Consequences:** A refactor that drops the AI-generated marking now fails CI instead of shipping. Art. 50 is a continuing obligation, so this protection matters after 2 August, not only before it. Component tests are now possible for other product-critical affordances (the approval gate, source links); nothing obliges them to exist, but the cost is no longer "add a test framework first".

**Explicitly NOT decided here — legal applicability.** This is a source-level engineering verification: it establishes that the documented mechanisms exist and cannot be bypassed. Whether Art. 50(2) applies to HITL-approved summarisation at all, and whether the "assistive function / no substantial alteration" carve-out is engaged, is a question for counsel and is not answered by this ADR. Art. 50(1) (informing a person they are interacting with an AI system) is not triggered by today's surfaces, but the planned "Ask This Meeting" conversational surface (Wave 1) would engage it and must be assessed before it ships.

**Amendment (2026-08-10) — the Art. 50(1) assessment this ADR left owed, for "Ask This Meeting".**

This ADR closed with: *"Art. 50(1) ... is not triggered by today's surfaces, but the planned 'Ask This Meeting' conversational surface (Wave 1) would engage it and must be assessed before it ships."* BACKLOG C9 made that a release gate, due at the next tag. `SummaryPanel` mounts `AskPanel` whenever a transcript exists, so 1.1.0 would be that tag. The assessment:

**The surface does engage Art. 50(1).** It is a conversational surface a person types into and receives generated answers from — an AI system intended to interact directly with a natural person. No carve-out is claimed; the "obvious to a reasonably well-informed person" exception is not relied on, because relying on it would be an argument rather than a control.

**What was already there, and what was not.** `AskPanel` already rendered an always-on, non-dismissable note reading *"AI-generated · review required"*, unconditional and above the input. That is an Art. 50(**2**) content marking. Art. 50(**1**) is a different obligation — informing the person that they are *interacting with an AI system* — and the wording only implied it. Implication is not disclosure.

**What changed.** The note now opens *"You are asking an AI assistant · answers are AI-generated and need your review"*, and its accessible name carries both halves. Three properties matter and each is now asserted separately, because a single check over both would stay green if either half were dropped:

1. **Present before interaction.** It renders unconditionally above the input, not after an answer arrives — being told afterwards is not being informed that you are interacting with an AI.
2. **Not dismissable.** No control inside the note, and no dismiss/close affordance in the panel.
3. **Both obligations stated.** The interaction disclosure and the content marking are distinct assertions in `AskPanel.test.tsx`.

**Proven, not asserted.** The tests were confirmed load-bearing by mutation — dropping the interaction sentence, dropping the interaction half of the accessible name, and gating the note on an answer having arrived each turn the suite red. **Still not decided here.** The two counsel questions this ADR opened are untouched: whether Art. 50(2) reaches HITL-approved summarisation, and whether the assistive-function carve-out is engaged. This amendment discharges the engineering obligation C9 named — the disclosure exists, holds on every reachable path, and cannot regress silently — and nothing more.

**Status:** Accepted (2026-07-26). Verification PASS; Art. 50(1) assessment for the Ask surface completed 2026-08-10 (amendment above); the Art. 50(2) applicability question remains for counsel.

## ADR-0033 — Tier-0: one honest device-capability probe, and a seam OS-native backends slot into

**Context:** The strategy's Tier-0 item (`STRATEGY_2026-2030.md`, Dalga 0) is a model/STT abstraction that makes OS-native small-model runtimes — Apple Foundation Models, Windows ONNX / Copilot Runtime — interchangeable with the built-in GGUF sidecar and BYOK cloud, selected per task from device capability. That wave is the largest tailwind behind the local-first thesis: it turns on-device inference from a quality tax into zero marginal cost.

Two findings shaped the scope:

1. **The LLM path has no hardware awareness at all.** `audio::HardwareProfile` (GPU type, performance tier) exists but lives inside `audio/` and is consumed only by the whisper engine. `summary/` — provider enum, `ProviderParams::call`, `assemble_provider` — never consults it. There is no shared answer to "what can this device run".
2. **Part of the existing detection does not detect.** `hardware_detector.rs::detect_memory_gb()` returns a hard-coded `8` unless a `MEMORY_GB` env var is set, and `PerformanceTier` is derived from it — so the tier is fictional on most machines.

The OS-native backends themselves cannot honestly be built in this environment: Apple Foundation Models needs macOS 26+ on Apple Silicon and Swift FFI (no macOS machine here — the §4 macOS smoke is still owed), and a Windows ONNX LLM path needs its own model-management and quality validation. Writing either would be unverifiable speculation.

**Decision:** Land the capability probe and the selection seam; declare the OS-native backends without implementing them. New dormant module `frontend/src-tauri/src/inference/`, pure and offline, called by nothing.

- **`capability`** — `DeviceCapabilities` (OS, arch, cores, RAM, GPU, NPU) with RAM measured through `sysinfo` (already a dependency) rather than assumed, plus a coarse `LocalInferenceFitness` for backend preference and product copy.
- **`backend`** — `LocalBackend` { `GgufSidecar`, `AppleFoundationModels`, `WindowsOnnxRuntime` }, a `BackendStatus` per host, a preference order (OS-native first on its own host), and `select_local_backend`.

Two honesty rules are enforced structurally rather than documented:

- **"Could not tell" is not "none".** `NpuVendor::Undetermined` is distinct from `None`, and `is_known_present()` is false for both, so an undetected NPU can never be counted as a capability. macOS is settled by construction (every Apple Silicon part has a Neural Engine); Windows and Linux report `Undetermined` because PnP enumeration is not implemented here and could not be validated against a machine that actually has an NPU. Reporting `None` there would let the product tell a Copilot+ PC owner they have no accelerator.
- **A declared backend is unselectable.** `select_local_backend` is *derived* from `BackendStatus` rather than hand-written, so an unimplemented arm cannot be returned by construction. `os_native_backends_are_never_selectable_yet` and `a_selected_backend_always_has_a_provider` pin it.

NPU classification is a pure function over a device name, split from the platform enumeration that feeds it, so it is fully testable without the hardware. This matters because the risk is false positives, not misses: a first pass that substring-matched `"npu"` flagged **"Microsoft Input Configuration Device"** on the (NPU-less) development machine — `I·npu·t` contains it. Matching is token-based, and that exact device name is now a regression test.

**Consequences:** Both STT and the summary path now have one place to ask what the device can do, and the arrival of an OS-native backend becomes an addition — implement it, flip its status to `Available` — rather than a refactor of every call site, matching the dormant-seam approach of `sync/` (ADR-0012) and `agents/` (ADR-0013). Nothing changes behaviour: no new inference path, no call sites, no UI. The local-first invariant holds by construction since the module performs no I/O beyond reading host properties.

**Owed, deliberately not faked:** the Windows/Linux NPU enumeration shim (needs a machine with an NPU to validate); the Apple Foundation Models and Windows ONNX implementations; and wiring the probe into provider assembly and the UI. `hardware_detector.rs::detect_memory_gb` is left as-is rather than changed underneath the whisper tier — the new probe measures RAM correctly for its own consumers, and correcting the whisper path is an audio-side change that must be made with §4's care and its own smoke test.

**Amendment (2026-08-07, out of the #13 review).** Three corrections, each one the module's own stated principle being violated by its first implementation:

1. **Cores were hardware threads.** `available_parallelism()` counts logical execution units, so a 2-core/4-thread part cleared the four-core floor and an accelerated 4c/8t part could reach `Comfortable`. `physical_cores: Option<usize>` (from `sysinfo`) is now separate from `logical_threads`, and `effective_cores()` halves threads when the physical count is unknown — understating a non-SMT part rather than overstating an SMT one, because overstating is what wrongly clears the floor.
2. **Vendor branding was read as an accelerator.** The `intel(r) ai` substring matched `"Intel(R) AI Camera"`, feeding a phantom NPU into the fitness verdict — the same false-positive class as the `I·npu·t` case, in the code written to prevent it. Only the `ai boost` device name matches now.
3. **Apple Silicon was treated as sufficient for Foundation Models.** The API arrives in macOS 26, and `DeviceCapabilities` carried no version, so the documented "just mark it Available" step would have selected it on macOS 15. `os_version_major` is now probed and the backend reports `UnsupportedHost` below 26 — including when the version cannot be parsed, so it fails closed.

**Status:** Accepted (2026-08-07). Seam dormant; OS-native backends declared, unimplemented, and structurally unselectable.

## ADR-0034 — Speaker diarization: post-hoc, not in the live pipeline; models pinned like Parakeet; quality unverifiable until A5 has multi-speaker audio

**Context:** `docs/DESIGN_READAI.md` Phase E requires "its own ADR before any model ships (model licensing, §9)", and the owner's 2026-07-09 scope decision promoted diarization from a maybe to a priority enabler. It is also the most visible parity gap: every competitor labels speakers; Mityu has no speaker code at all. The owner chose the real-model path (2026-08-08) over the cheaper channel-attribution alternative, because channel attribution ("you" vs "the room") does nothing for in-person capture — which is precisely Mityu's differentiator.

Three findings from reading the tree shaped this decision.

1. **Channel provenance is destroyed before transcription.** `audio/ffmpeg_mixer.rs:319` mixes microphone and system audio into one stream (`(m * mic_ducking) + (s * system_gain)`) and `pipeline.rs:901` feeds the mixed window onward. Both sources still exist separately at that call, so a cheap two-way attribution was available — but it is worthless for a room recorded on one microphone.
2. **A transcript row is not a speaker turn, so a row cannot carry a speaker.** `TranscriptSegment` carries id, text, timestamp and audio timings and no speaker field; a dead `transcripts.speaker` **column** does exist in SQLite (added 2025-11-10 from upstream, never read or written). Re-purposing it would not work anyway: a row is one VAD speech segment, and VAD is tuned to *bridge* pauses rather than cut at them — the import and retranscription paths pass `VAD_REDEMPTION_TIME_MS = 2000` (`audio/import.rs:57`, `audio/retranscription.rs:52`), a longer gap than the one between two people taking turns, and `audio/import.rs` treats segments over 25 s as normal. One row therefore routinely spans several speakers, and talk-time — a sum of durations — cannot be derived from row labels at all.
3. **Saved audio is optional, so some meetings can never be diarized.** `RecordingSaver::start_accumulation(false)` discards every mixed chunk (`audio/recording_saver.rs:236-249`) and `stop_and_save` then returns without producing a file (`:434-440`). "Transcripts only" is a supported recording mode.
4. **`CLAUDE.md` §10 forbids refactoring the audio pipeline and the DB schema in one change**, and diarization needs both.

**Decision:**

1. **Diarization runs post-hoc on the saved recording, not inside the live capture pipeline.** Speaker clustering is inherently global — deciding that the voice at 02:00 is the same person as at 47:00 requires both — so a streaming implementation would be worse *and* would put new code in the most fragile subsystem in the app (`CLAUDE.md` §4). The saved audio already persists until the user deletes the meeting, so the live path is not touched at all.
2. **Model stack: `pyannote-segmentation-3.0` for segmentation plus a speaker-embedding model, obtained from the sherpa-onnx GitHub release assets**, not from Hugging Face. This matters: `huggingface.co/pyannote/segmentation-3.0` is **MIT-licensed but gated** — verified from the model card, which states "You need to agree to share your contact information to access this model". An app cannot satisfy a click-through gate on the user's behalf, so an in-app download from that origin is not viable. sherpa-onnx publishes converted ONNX artifacts at its `speaker-segmentation-models` and `speaker-recongition-models` release tags, which are stable, unauthenticated, and pinnable — exactly the shape `parakeet_engine` already consumes (revision-pinned, expected size and SHA-256 checked through `utils::verify_file_integrity`).
3. **Speaker identity is stored as timed turns, never as a label on a transcript row.** A new `speaker_turns` table holds `(meeting_id, workspace_id, speaker_label, start_ms, end_ms, confidence)`; the UI renders a row's speakers by overlapping it with turns, and talk-time sums turn durations. Overlapping turns are permitted, because people talk over each other and a diarizer should be able to say so. Turns are **local-derived and not synced** — ADR-0012 pins the synced set, and a peer can regenerate turns from audio; syncing them later requires amending ADR-0012. The dead `transcripts.speaker` column stays dead and is explicitly **not** the diarization surface.
4. **Diarization is offered only when the audio still exists, and availability is probed rather than stored.** A transcripts-only meeting (finding 3) has no input, and ADR-0027's retention goal means audio can also disappear *later* — so a stored availability flag would go stale on deletion. The check reuses `find_audio_file` (`audio/retranscription.rs:149`), which already solves the identical problem for retranscription. Four UI states follow: no audio → "not available for this recording"; audio with `diarized_at` NULL → offer to run; `diarized_at` set with no turns → inconclusive; set with turns → show them. `meetings.diarized_at` exists precisely so an empty turn list is not read as "no speakers found".
5. **Ship the schema before the engine, per §10.** Order: (a) this ADR; (b) the `speaker_turns` table plus `meetings.diarized_at`, populated by nothing; (c) the diarization engine and model download; (d) UI for speaker labels and talk-time. Each lands separately.
6. **Speaker labels stay anonymous and human-named.** The system emits `Speaker 1..N`; attaching a real identity is a manual human action. Mityu does no voice-based identification, and no emotion, charisma, engagement or performance inference is derived from them (`DESIGN_READAI` guardrail 3, `CLAUDE.md` §10). This is also what keeps the processing outside the "unique identification" purpose that would make it biometric special-category data under KVKK m.6 / GDPR Art. 9 — see `docs/legal/A5_KVKK_PACK.md` §4.1, where the same distinction is already drawn for the eval recordings.
7. **Talk-time is descriptive only** — seconds and share of the meeting, source-linked like every other derived figure. It is not a score, ranking, or judgement of any participant.

Verified in sqlite3 with foreign keys ON — the one state production negates. `speaker_turns` is unpopulated so nothing was retained, but `correction_events` (ADR-0030) had the identical defect and *was* live. Both are now deleted explicitly and guarded structurally; see the ADR-0030 amendment of the same date.

**Review correction (2026-08-08, before merge):** the first draft of this ADR stated that no speaker field existed and proposed storing one anonymous label per transcript row. Review found both wrong: a dead `transcripts.speaker` column does exist, and — more importantly — VAD's 2000 ms redemption means a transcript row routinely spans multiple speakers, so row labels would mis-attribute speech and could not produce talk-time. The draft also assumed saved audio always exists, which "transcripts only" recordings disprove. Findings 2–3 and decisions 3–5 above are the corrected text; nothing had been merged or applied when they changed.

## ADR-0035 — Diarization engine: the sherpa-onnx pipeline, run out-of-process to keep a second ONNX Runtime out of the capture process

**Context:** ADR-0034 fixed the *shape* of diarization (post-hoc, timed `speaker_turns`, anonymous labels) and deliberately left the implementation approach open: `sherpa-rs` bindings versus writing segmentation post-processing and clustering ourselves on `ort`. That question is now answered, and the measuring instrument it depends on exists — `eval-harness`' DER scorer, validated against NIST `md-eval.pl` on 216 VoxConverse recordings, agreeing at the printed 0.01 pp resolution on all 1296 comparisons per collar (`docs/DIARIZATION_EVAL.md`).

Three things that were *assumed* when ADR-0034 was written turned out to be wrong, and each changes the decision:

1. **`sherpa-rs` is dead.** The crate named in ADR-0034 is archived read-only (last push 2026-03-08, 32 open issues); its README points at k2-fsa's own `sherpa-onnx` crate. The live crate is `sherpa-onnx` 1.13.4, **Apache-2.0**, published 2026-07-08, from the upstream repository.
2. **No Rust crate can be added to the app that does the job on `ort`.** `speakrs` (Apache-2.0) genuinely implements the full pipeline, but requires `ort ^2.0.0-rc.12` while the app's VAD dependency pins it exactly: `silero_rs` (rev 26a6460) declares `ort = "=2.0.0-rc.10"`, and `ort-sys` declares `links = "onnxruntime"`, so only one may exist in the graph. `pyannote-rs` is the only rc.10-compatible candidate and is not a diarizer — no powerset decode, no clustering; it benchmarks at 80% DER.
3. **ADR-0034's licence route was based on a gate that does not bind us.** `pyannote/segmentation-3.0` is MIT but access-gated on Hugging Face; sherpa-onnx republishes converted ONNX artifacts on unauthenticated GitHub release tags, which is the origin ADR-0034 already blessed.

**Decision:**

1. **Integrate the assembled sherpa-onnx pipeline via k2-fsa's official `sherpa-onnx` crate (Apache-2.0), not `sherpa-rs`, and not a hand-written pipeline on `ort`.** Segmentation → embedding → clustering is a research project to write and an integration to adopt; we have no way to justify the former while the thing it would buy — tunability — is unmeasurable against target-condition audio we do not yet have.

2. **It runs OUT OF PROCESS, in a `diarize-helper` sidecar binary.** Measured on Windows MSVC (2026-08-09):

   | Configuration | Result |
   |---|---|
   | `sherpa-onnx` alone, default (`static`) | **Links, runs, exit 0.** Zero linker warnings on a forced relink. |
   | `sherpa-onnx` (`static`) **+ `ort = "=2.0.0-rc.10"` in one binary** | **`LNK1169: multiple defined symbols`** — fatal. |
   | `sherpa-onnx` (`shared`) **+ `ort` in one binary** | **Links and runs.** Both FFI boundaries crossed. |

   The `static` combination fails with exactly the predicted class — `LNK2038: 'RuntimeLibrary' mismatch: MT_StaticRelease vs MD_DynamicRelease` against `libort_sys(onnxruntime_c_api.obj)`, plus `LNK2005` duplicate C++ runtime symbols and `LNK4098 defaultlib 'LIBCMT' conflicts` — because sherpa's Windows archive is `…-win-x64-static-MT-Release-lib.tar.bz2`, a static-CRT build, while `ort` brings a `/MD` one.

   **The third row is why this decision is not "forced".** An earlier draft of this ADR said two ONNX Runtimes "cannot share one binary"; that is false, and only the `static` row had been measured when it was written. With sherpa's `shared` feature the combined binary links, runs, and initialises both sides. So the sidecar is a **choice**, and it has to be justified on its merits rather than on a linker error:

   - **In-process would put a second ONNX Runtime instance in the app's own process.** Measured: `ort` links its runtime *statically* (`cargo:rustc-link-lib=static=onnxruntime`, ONNX Runtime 1.22.0 — `ort::info()` reports `rel-1.22.0` at run time) while sherpa loads *its own* `onnxruntime.dll` from the shared archive. Two independent runtimes, two sets of global state, in the process that also runs capture and transcription — `CLAUDE.md` §4's most fragile subsystem. Nothing was run through actual inference in either, so that combination is **unproven, not merely inelegant**.
   - **Packaging.** In-process `shared` puts **39 MB of loose DLLs** beside the app (`onnxruntime.dll` 17.4 MB, `DirectML.dll` 18.5 MB, `sherpa-onnx-c-api.dll`, …). The sidecar is **one 17.7 MB self-contained file**.
   - **It would couple Parakeet's runtime to sherpa's**, which is what the `silero_rs` → `ort = "=2.0.0-rc.10"` pin exists to prevent.

   Separate processes have separate address spaces, so the sidecar removes all three at once: **zero lines change in `parakeet_engine`, the `silero_rs` `ort` pin is untouched, no `ndarray` 0.16→0.17 migration.** The repo already ships two sidecars (`binaries/llama-helper`, `binaries/ffmpeg`, `externalBin` in `tauri.conf.json`, manager in `summary/summary_engine/sidecar.rs`), so this is an existing pattern, not a new one. Diarization is a *better* fit than `llama-helper`: ADR-0034 makes it post-hoc and whole-file, so it is one invocation per meeting with no keep-alive.

3. **Default (`static`) features, giving a single self-contained executable.** Measured: 17.7 MB release, and it runs from an otherwise **empty directory** — no `onnxruntime.dll`, no sibling libraries to ship or to get out of step. One file into `binaries/`, exactly like the two already there. The `shared` feature is available and not needed.

4. **The native archive MUST be verified before `sherpa-onnx-sys` is ever built — and NOT by a build script of ours.** `sherpa-onnx-sys`' `build.rs` downloads a prebuilt archive from a GitHub release and performs **no integrity check of any kind** — verified by reading it. That is squarely against ADR-0020's exact-size-plus-digest precedent for model files.

   The obvious mitigation does not work, and the trap is worth stating so nobody implements it: a `build/ffmpeg.rs`-style check inside `diarize-helper`'s own build script runs **too late**. Cargo builds a dependency's script before the dependent crate's, and a build script cannot set environment for a sibling that has already run — so the unverified bytes would be downloaded and extracted before our digest check executed.

   So the verification must sit **outside cargo**, in one of two places:
   - a **bootstrap step run before `cargo build`** (developer command and CI step) that fetches the archive, checks **exact byte length and SHA-256** against a pinned release tag and URL — the full ADR-0020 precedent, not a digest alone — fails closed on mismatch, and hands it over through the documented `SHERPA_ONNX_ARCHIVE_DIR` / `SHERPA_ONNX_LIB_DIR`; or
   - a **vendored/patched `sherpa-onnx-sys`** whose build script does the check itself.

   The bootstrap is preferred: it leaves the upstream crate untouched and therefore upgradable. **Built 2026-08-09** as `tools/diarization/fetch-sherpa-archive.py`, wired into `ci.yml` behind a `Cargo.lock` guard so it activates by itself when the helper lands.

   **This is a prerequisite for making `diarize-helper` a workspace member, not merely for shipping.** `ci.yml:36-38` runs `cargo clippy --all-targets` and `cargo test --all` on `ubuntu-latest` for every push and pull request, so from the moment the helper joins the workspace, **every PR performs the unverified download this decision forbids** — on a runner, unattended. Adding the crate before the bootstrap exists is therefore the wrong order, not a shortcut.

5. **Speaker count is never assumed.** `FastClusteringConfig::default()` is `num_clusters: -1, threshold: 0.5` — read from the crate source and confirmed at run time. `-1` means "unknown, cluster by threshold". A fixed default would have imposed a speaker count on every meeting, and a two-person conversation is Mityu's typical recording; if a future version changes that default, this is the line to re-check.

6. **The result SHAPE matches the schema; the units and the label do not, and the conversion is part of this contract.** `OfflineSpeakerDiarizationSegment { start: f32, end: f32, speaker: i32 }` is one timed turn per row, which is exactly what ADR-0034 decided independently — so no re-modelling is needed. But it is **not** a copy:

   | sherpa | `speaker_turns` | conversion |
   |---|---|---|
   | `start`/`end`: `f32` **seconds** | `start_ms`/`end_ms`: `INTEGER` **milliseconds** | `(secs * 1000).round() as i64`. Storing the float directly would place every turn ~1000× too early. |
   | `speaker`: `i32` index, 0-based | `speaker_label`: `TEXT`, e.g. `Speaker 1` | `format!("Speaker {}", speaker + 1)` — anonymous, 1-based for humans (ADR-0034 decision 6). Storing `0` would put a bare integer where the report renders a name. |
   | (not reported) | `confidence`: `REAL` nullable | `NULL`. The engine reports no per-turn confidence, and NULL means "not reported", which is not the same as "low". |

   A turn whose rounded `end_ms <= start_ms` is dropped rather than stored.

**How the evidence was obtained, and one thing it corrects:** two throwaway crates outside the workspace (`C:\t\spike-diarize`, `C:\t\spike-both`), so a failed spike could not touch CI. The first version of the standalone spike only printed a string; it linked and produced a **128 KB** binary, because with nothing referencing sherpa the linker's `/OPT:REF` had discarded the entire library — a false pass that would have proven nothing. Calling `OfflineSpeakerDiarization::create()` took it to 21.4 MB and produced errors from sherpa's own C++ source (`offline-speaker-segmentation-model-config.cc:Validate:38`), which is what proves the FFI boundary was crossed at run time rather than merely satisfied at link time. `create()` returned `None` on bad configuration instead of aborting — a native library that crashed there would be unusable in a sidecar.

The earlier analysis called the `/MT` clash "the kill risk" for the standalone build. It is not: standalone links cleanly. It is fatal only for the **in-process `static`** build — and, as decision 2 records, not for the in-process `shared` build, which links and runs. So the linker settles one configuration, not the architecture; decision 2 rests on the runtime-coupling and packaging grounds stated there.

**Consequences:** **+** The live capture path is untouched (`CLAUDE.md` §4 risk nil); the app's `ort`/`ndarray`/`silero_rs` graph is untouched; reversibility is deleting one workspace member and one `externalBin` entry; the engine can be swapped later without touching the app. **−** ~18 MB on the installer; a second, independently-versioned ONNX Runtime to keep an eye on; and one more binary to sign.

**What this ADR does NOT authorize:**

- **Shipping.** Decision 4 (the archive integrity bootstrap) is a prerequisite and is not built. ADR-0034's item 2 — primary-source licence verification — **is now discharged**; see its 2026-08-09 amendment.
- **Any speaker-accuracy claim.** ADR-0034's ban stands: the A5 `multi` bucket holds zero recordings, and the DER scorer is validated on English broadcast audio, not a Turkish meeting room.
- **macOS.** Only Windows was measured here. `ci.yml` does build and test on `ubuntu-latest` for every push and PR, so a **Linux** break would surface immediately — but **macOS is built by neither `ci.yml` nor `release.yml`** (`build-macos.yml` is dispatch-only), so a macOS break would surface at release or later. A macOS check for the helper is owed as part of the implementation; a Windows one is owed because `ci.yml` does not build Windows either.
- **Any statement about runtime or memory on a 60–90 minute recording.** Unmeasured; clustering is superlinear in segment count, and this determines whether the sidecar needs chunked progress reporting.

**Status:** Accepted (2026-08-09). Closes the implementation-approach question ADR-0034 left open, and supersedes that paragraph only. ADR-0034's item 2 (model provenance) is untouched; its licence-verification obligation was **discharged on 2026-08-09** — see that ADR's amendment of the same date — so the one remaining shipping prerequisite here is decision 4's archive integrity bootstrap.

## ADR-0036 — Talk time is a share of *speech*, not of the meeting; speakers are listed in the order they spoke, never ranked

**Context:** ADR-0034 step (d) — the UI for speaker labels and talk time — leaves two numeric decisions open that look like formatting and are actually claims about people.

**Decisions:**

1. **The denominator is the sum of attributed speech, not the meeting's duration.** People talk over each other, so speaking time exceeds elapsed time: 30 s of recording with a 10 s overlap contains 40 s of speech, and shares over duration would read 100% and 33%, summing to 133%. Dividing by total speech makes the shares sum to 1 and makes them true. The screen states which denominator it is and why, because "40%" with an unstated denominator is the part a reader fills in wrongly.

2. **Each speaker's own time is the UNION of their turns**, not the sum. Segmentation can emit turns for one speaker that overlap themselves; summing would credit that speaker twice for one stretch of audio.

3. **Speakers are ordered by first appearance. Never by duration.** Sorting by talk time turns a description into a leaderboard, and a leaderboard of who talked most is the employee-performance reading `CLAUDE.md` §10 and ADR-0034 refuse. The panel says outright that speaking time is not a measure of contribution. Colour is assigned by that same order and identifies a speaker across the page; the palette is deliberately flat, with no red/green and nothing that reads as good or bad.

4. **A transcript row is attributed to a LIST of speakers, never to one.** Rows and turns come from separate passes over the same audio and do not align — the `speaker_turns` migration says so in its own note. Choosing "the dominant speaker" would print one confident name over a stretch where two people spoke. Overlaps below **250 ms, or 15% of the row for short rows**, are discarded as boundary artefacts: without a floor, touching edges put two names on nearly every row, which reads as constant crosstalk and hides the genuine overlaps.

5. **A row with no timings shows nothing at all**, not "Unknown". Recordings predating recording-relative timestamps have no extent to match against, and an empty space says "we cannot tell" where a chip would assert something.

6. **The four states stay four.** No audio / never ran / ran-and-separated-nothing / has turns each get different words, and only the states where an action is possible show a button. Collapsing "ran and found nothing" into "never ran" — the natural mistake, since both have an empty turn list — would either keep offering a pass that already happened or tell someone their single-voice recording was never analysed. This is why the repository stamps `diarized_at` even for an empty result.

**Verification:** the arithmetic is pure and unit-tested (`frontend/src/lib/speakerTurns.test.ts`), and the tests were confirmed load-bearing by mutation: sorting by duration, attributing a row to only its dominant speaker, summing instead of unioning, and dropping the overlap floor each fail the suite. The rendered claims are asserted in `SpeakerTurns.test.tsx` so a redesign cannot quietly drop the caveats. The screen itself was **looked at**, not just typechecked, via `tools/ui/shoot.py` against `/design/speakers`, which renders all four states from fixture data.

**One thing the screenshot found that no test would have:** `text-display`, `text-body`, `text-small` and `text-caption` are used across the report and `/design/*` screens as if they were a type scale, and are **defined nowhere** — they emit no CSS. Measured in a browser, an `<h1 class="text-display">`, a `.text-small` and a `.text-caption` all compute to `16px / weight 400`, identical to `body`; the apparent hierarchy comes entirely from font weight and colour. The two files added here were converted to real utilities; the other five were left for their own change, made in ADR-0037.

**What this does NOT authorize:** any claim about *accuracy*. ADR-0034's ban stands — the A5 `multi` bucket holds zero recordings, so how often these labels are right is unmeasured on this project's own audio. It also does not add naming: there is no field, and no button, to attach a person to a voice.

**Amendment (2026-08-09, same day, after review):** four corrections, all of them claims the screen was making that the code or the rules did not support.

1. **A row with two speakers is not crosstalk.** The chip said `overlapping` on every multi-speaker row, but most such rows merely span a handover — turns `[0, 5s]` and `[5s, 12s]` are sequential and do not overlap each other at all, so an ordinary change of speaker was being described as people talking over one another. `hasCrosstalk()` now asks whether two *different* speakers' turns actually intersect inside the row (100 ms floor, below which it is rounding), and only genuine simultaneous speech is marked, as "at the same time". Two chips already say "two speakers"; a word there added nothing but a false claim.

2. **The result is labelled best-effort on screen.** ADR-0034 states that "the feature ships labelled best-effort" until the A5 `multi` bucket is collected and reviewed. That bucket still holds zero recordings. Decision 7 of this ADR said accuracy was not claimed — but saying so in an ADR does not discharge a rule about **product copy**. The panel now says the separation is a best-effort estimate whose accuracy has not been measured on the reader's own recordings.

3. **A failure to ask was invisible.** The hook correctly reported a failed availability query as an `error` with no state — and the panel then gated the entire block on that state, so a database or command failure made the whole feature vanish silently. A reader could not tell "this meeting has no speakers" from "we could not find out", and only the second has a retry. The error now renders independently, with a Try again.

4. **The download button understated the download.** It said 34 MB, which is the on-disk total; the segmentation model arrives as a `.tar.bz2` and expands, so 35.2 MB actually crosses the network. Corrected to 35 MB and pinned by `models::tests::the_download_size_the_ui_promises`, so bumping a model pin fails the build instead of leaving the button quietly wrong.

Each correction carries a test, and each test was confirmed load-bearing by restoring the defect and watching the suite fail.

**Status:** Accepted (2026-08-09). Implements ADR-0034 step (d).


## ADR-0037 — The named type scale was never real; the app's one typography vocabulary is Tailwind's own

**Context.** ADR-0036 recorded that `text-display`, `text-body`, `text-small` and `text-caption` were used as a type scale and defined nowhere — not in `globals.css`, not in the Tailwind config, absent from the built CSS. Two files were converted then; five were left. Reading those five turned up two more of the same kind, `text-h1` and `text-h2` (10 occurrences), which the original count missed. Two of them are the `<h1>` page titles of `/design/hitl` and `/design/learning`: because Tailwind's preflight resets `h1` to inherit size and weight, those titles rendered at `16px / 400` — the page heading was the same size as its own subtitle.

**Decision.** Delete the vocabulary rather than implement it. The six names were replaced with Tailwind utilities:

| was | now | computes to |
|---|---|---|
| `text-display` | `text-2xl font-semibold` | 24 / 600 |
| `text-h1` | `text-xl font-semibold` | 20 / 600 |
| `text-h2` | `text-lg font-medium` | 18 / 500 |
| `text-body` | `text-[15px]` | 15 / 400 |
| `text-small` | `text-sm` | 14 / 400 |
| `text-caption` | `text-xs` | 12 / 400 |

**Why not define the scale instead.** It was the other option and it loses on three counts. (1) **There is no design system to make real.** `docs/DESIGN_READAI.md` — the doc the vocabulary was assumed to come from — contains no typography section, no tier names and no sizes. Nothing in the repo defines these names. Implementing them would have been inventing a design system and backdating it, not honouring one. (2) **It would create a second vocabulary, not a first.** The app already has one: Tailwind's scale, ~640 usages across 99 of 149 `.tsx` files. The six phantom names survived in five, all but one of them `/design/*` preview routes. Adding `text-body` alongside `text-base` and `text-small` alongside `text-sm` gives two ways to say one thing, and the smaller one is the newcomer. (3) **The mechanism assumed doesn't exist here.** This project is on Tailwind **3.4.19** with a `tailwind.config.js`; `@theme` and `@utility` are v4 features. It was still doable via `theme.extend.fontSize`, but the premise was wrong and worth stating.

The first-order argument is simpler: two files had already been converted this way, and consistency with what shipped beat consistency with what was imagined.

**The one thing that changed beyond a rename.** `/design`'s typography specimen advertised sizes it did not render — "Display — 32 / 700" on a line computing to 16/400. Since the mapping puts display at 24/600, applying it verbatim would have replaced one false label with another. Each row now prints the utilities it uses (`Display — text-2xl font-semibold — 24 / 600`), so the label cannot drift from the line again.

**Verification — measured, not typechecked.** `tsc`, `next lint` and 176 vitest tests all passed *before* this change too; they cannot see a class that emits no CSS. So each route was built and measured in headless Chrome via `getComputedStyle`, the check that found the bug, with a control: an element carrying the *old* class name injected into each rendered page. On every route all six controls still compute to `16px / 400` while every converted element resolves to its intended size — one measurement showing both that the names were dead and that the replacements are live. `/design`, `/design/report`, `/design/hitl`, `/design/learning` and `/settings` (for `ThemeToggle`) were each verified, and the four `/design` routes screenshot with `tools/ui/shoot.py`.

**Known gap, not fixed here.** Nothing prevents the next `text-h3`. An undefined utility is invisible to `tsc`, to `next lint` and to any test that does not rasterize — which is how these survived. A check that greps `className` for `text-*` tokens absent from the built CSS would close it and does not exist yet.

**Status:** Accepted (2026-08-09). Completes the cleanup ADR-0036 deferred.

A5 remains mandatory before those. The next release that wants to broaden validated scope needs the real human artifacts, not another ADR.

## ADR-0038 — Live Copilot: private, not covert — in-meeting assistance without the deception features of its category

**Context:** The owner asked (2026-09-11) for a gap analysis against Cluely and its open-source clones, and a plan to close the gaps. The analysis is recorded in `docs/COMPETITIVE_CLUELY_GAP.md`; the executable tasks are BACKLOG **EPIC I**. Four findings shaped this decision:

1. **The gap is a category, not a feature.** Everything Mityu does happens *after* capture: source-linked summaries (C1), action items (C2), Evidence Search (C3a), Action Center (C3b), export (C4), even "Ask This Meeting" (Product Intelligence slice 3) runs over a finished transcript. The competitor category is defined by help *during* the conversation — a private always-on-top panel with "what should I say next", follow-up questions, a live recap, fact-checking against a knowledge base, and screen context — plus meeting modes and post-call recipes. Cluely's documented surface (`docs.cluely.com`: Live Insights, Pre Call Briefs, Meeting Notes, Knowledge Base, Customization Suite, Role Management, CRM/ATS Integrations, Undetectability) confirms the shape; the reference repository (Natively) shows one working architecture for it.
2. **The category's signature feature is deception, and it does not even work.** "Undetectable" overlays, process-name disguise, dock/taskbar hiding and keyboard hooks that type without taking focus exist to hide an assistant from other people in the room or from proctors. That contradicts `CLAUDE.md` §0.6 (consent is architectural), the EU AI Act Art. 50 posture Mityu has verified (ADR-0032), and the KVKK stance in `docs/SECURITY_PRIVACY.md`. It is also technically hollow on macOS: since macOS 15 ScreenCaptureKit ignores `NSWindow.sharingType = .none`/`setContentProtection` (Apple DTS, developer forums thread 792152: *"At this time there are no public APIs for preventing screen capture"*; tauri-apps/tauri#14200, open, upstream). Windows `WDA_EXCLUDEFROMCAPTURE` does work (Windows 10 2004+; older versions render a black box); Linux has no equivalent. A product that promised invisibility would be lying on one of its two supported platforms.
3. **The reference code cannot be used, only learned from.** Natively ships under the *Natively Personal Use Source License v1.0* (non-commercial only); Glass, Cue, Cheating-Daddy and the old Pluely releases are GPL-3.0. Mityu is a commercial MIT product; none of that code, and none of those prompts, may be copied. The permissively licensed building blocks are Tauri's own window APIs (`set_content_protected`, `always_on_top`, `transparent`, `set_visible_on_all_workspaces`, `set_ignore_cursor_events`), `tauri-plugin-global-shortcut` (MIT/Apache), `tauri-nspanel` (MIT/Apache; used in production by Cap and Screenpipe) and `xcap` (Apache-2.0).
4. **Most of the substrate already exists.** `TranscriptUpdate` already carries `source` (`microphone`/`system`), `is_partial` and recording-relative timings (`audio/transcription/worker.rs:30`); `transcript-update` is already an app-wide event that Rust code subscribes to (`recording_commands.rs:323`); `ask::grounding` already implements "drop, never repair" citation checking; the `summary/` provider layer is already BYOK with a built-in local model; `redaction::redact` already sits at the prompt boundary; `summary/templates` already loads built-in and user-authored templates; the recording consent ticket (`recording_consent.rs`) already gates every capture start. The copilot is mostly a new *consumer* of existing seams.

**Decision:** Build the live copilot as BACKLOG EPIC I, under four invariants that are enforced structurally and re-verified at the I9 gate, and with an explicit reject list.

*Invariants*

1. **Private, not covert.** The `copilot` window is content-protected for the user's *privacy* (their private notes must not leak into a screen share) and carries an honest per-platform indicator — Windows "hidden from screen share (Windows 10 2004+)", macOS "best-effort: macOS 15+ may still capture this panel", Linux "not supported". The app never hides its own existence: no `skip_taskbar` hiding, no process renaming, no keyboard hooks, the recording indicator stays visible, and the word "undetectable" never appears in product copy or marketing.
2. **The copilot never captures on its own.** It consumes only the `transcript-update` stream of a recording session whose consent ticket was consumed; there is no separate listening mode; no task in EPIC I modifies `audio/` (CLAUDE.md §4). Screen context is a single, user-initiated, previewed and confirmed capture — never continuous, never on a timer, never persisted by default.
3. **Every insight is an AI-labelled, source-linked, non-persisted draft.** Art. 50(1) disclosure on first open and a non-dismissable Art. 50(2) marking on every card (the ADR-0032 test pattern); every claim cites a transcript segment (`source_chunk_id`) or, once I5 exists, a knowledge chunk; the `ask::grounding` rule holds — a citation outside the retrieved window is dropped, never repaired; an empty window yields a refusal, never an empty answer; the only persistence is "Pin to notes", which writes a **draft** block with `source_chunk_id` into `summaries.sections` through the existing repository (status forced `draft`, the C1 rule). There is deliberately **no** copilot table. The copilot produces text and nothing else: no tool calls, no sends, no writes to external systems (CLAUDE.md §10; OWASP LLM01 — transcript, screen and knowledge text are untrusted input).
4. **Flag-gated, default OFF, quality-gated ON.** Mechanics land behind the `liveCopilot` beta flag (with it off: no shortcut registered, no window created, byte-identical behaviour — the `sync/`/`agents/`/`inference/` dormant-seam precedent). This may happen before A5/C8 on the same basis as C1/C3a (ADR-0019, ADR-0024): the mechanics are transcription-quality-independent. **Defaulting the flag ON, and any "live help" or latency claim, requires A5 GO plus the I9 gate** (network-OFF smoke, live smoke on real consented meetings with latency and citation-validity measured, Art. 50 tests, `/security-review`, multitenancy-guardian). The copilot does not pass A5; A5 unlocks the copilot.

*Where the code goes* — `frontend/src-tauri/src/copilot/` (`window.rs`, `session.rs`, `insights.rs`, `policy.rs`, `commands.rs`), `knowledge/` (documents, chunks, FTS5 derived index — the `transcript_search_*` pattern of ADR-0024/0026), `modes/` (a superset of `summary/templates`), `screen/` (`xcap` + OS-native OCR behind the ADR-0033 capability seam), `usage/` (content-free `usage_events`); frontend `app/copilot/` loaded by the second window from the static export, `services/{copilot,knowledge,modes,usage}Service.ts`, a Copilot settings tab, a Knowledge tab and a Modes editor. `ask::grounding`'s `SourceRef` gains `Knowledge` and (non-persisted) `Screen` kinds under the same rule.

*Schema* — `knowledge_documents` and `knowledge_chunks` are SYNCED-class tables (common + sync columns from day one) so a Phase-2 admin-managed team knowledge base (the competitor's "Customization Suite") is additive; `knowledge_search_*` and `usage_events` are local-only. Every schema change ships as its own PR, never with an audio change (CLAUDE.md §6/§10).

*Sequence* — I0 (this ADR) → I1 window shell + global shortcuts → I2 deterministic live context ∥ I4a modes registry → I3 on-demand insights (Suggest · Follow-ups · Recap · Define) → I5 local knowledge base (enables "Fact check" against transcript + knowledge only) → I6 screen context → I8 opt-in proactive offers, usage ledger, local pre-call brief (brief waits for G2) → I9 gate. I7 (deterministic recipes over approved content, cross-meeting recall, manual speaker names) is independent of the I-series and builds on C1/C3b/H6.

*Rejected, with the reason recorded rather than implied*

| Rejected | Why |
|---|---|
| Undetectability, stealth mode, process disguise, dock/taskbar hiding, keyboard hooks | Deception; §0.6; unreliable on macOS 15+; keyboard hooks are a keylogger-class security surface |
| Candidate-side interview/exam assistance, coding-interview solver modes | Assessment integrity; brand risk; contradicts the regulated-enterprise beachhead |
| Continuous screen recording (Rewind/Screenpipe model) | Privacy, storage, KVKK; screen context is one previewed frame |
| Web research/profiling of meeting participants ("who am I talking to") | Third-party personal data; the local version (calendar metadata opt-in + prior meetings + open approved items) gives the value without it |
| Web fact-checking by default | Egress; a future opt-in BYOK search needs its own ADR |
| Post-call "coaching" and communication-gap scores | Emotion/performance inference boundary (`DESIGN_READAI.md`; EU AI Act); the reference product switched its own off as low-value |
| Autonomous send / CRM write / calendar change | HITL (§0.5, §10); approval-gated push lives in EPIC G |
| Cloud-proxied OAuth for calendar | ADR-0018 requires client-direct OAuth with tokens in the OS keychain |
| Copying Natively or GPL code/prompts | Licence incompatibility with a commercial MIT product |

**Consequences:** Mityu gains the category's genuine value — help while the conversation is happening — on the one axis the category cannot follow: consent-grade, source-linked, human-approved and honest about what the OS can and cannot hide. `CLAUDE.md` §1's "not a meeting bot" is unchanged (the copilot joins nothing and captures nothing new). `ROADMAP.md` gains Phase I; `STRATEGY_2026-2030.md` §2 gains the corresponding parity rows. Costs accepted: a second window and a global-shortcut plugin widen the desktop surface; a knowledge base doubles as a second copy of user documents inside SQLCipher (same posture as the FTS index, ADR-0026); the live experience is bounded by the capture pipeline's VAD segmentation (seconds, not milliseconds — no latency figure is published without I9's measurement); any streaming/latency work in `audio/` is a separate, §4-smoked change.

**Status:** Accepted as design direction (2026-09-11; owner review pending). I0 satisfied by this record; I1–I9 tracked in BACKLOG EPIC I; `liveCopilot` default OFF until I9.

## ADR-0039 — The live context follows the transcript producer, not the plan: every emission is final, and no segment is attributed to a device yet

**Context:** Building BACKLOG I2 (2026-09-13) against the actual producer of `transcript-update` (`frontend/src-tauri/src/audio/transcription/worker.rs`) showed that two premises written into ADR-0038 finding 4 and into the I1/I2 acceptance criteria are false:

1. **`TranscriptUpdate.source` does not carry `microphone`/`system`.** The worker hardcodes `source: "Audio".to_string()` for every segment (`worker.rs`, the single `TranscriptUpdate { … }` construction). There is no me/them signal in the stream. I1 had already run into this on the panel side and shipped the tail unattributed; I2 is where the service layer met the same fact.
2. **`is_partial` is not a lifecycle.** Whisper sets it as `duration_seconds < 15.0` (`whisper_engine/whisper_engine.rs:738`); Parakeet never sets it. Each chunk is emitted exactly once with a fresh `sequence_id` from a shared counter, and nothing later replaces it. The live VAD closes a segment after **400 ms** of silence (`audio/pipeline.rs`'s `redemption_time`; the 2 000 ms `VAD_REDEMPTION_TIME_MS` belongs to the offline import and retranscription paths only, as ADR-0034 states), so nearly every real utterance is far shorter than 15 s and therefore flagged "partial". The main transcript view (`TranscriptContext.tsx`) already treats every emission as one segment and de-duplicates by `sequence_id`; the recording saver stores all of them. The I1 panel had implemented the plan's reading and was **dropping `is_partial` segments — hiding most of the meeting**.

A third fact shaped the buffer, and the first draft of this record got it **wrong**: it claimed three transcription workers run in parallel, so that `sequence_id` would not follow audio time. The producer does the opposite — `worker.rs`'s `const NUM_WORKERS: usize = 1; // Serial processing ensures transcripts emit in chronological order` — so emission order and audio order coincide today. (The claim came from the stale `"workers": 3` literal in the `recording-started` payload, which describes nothing; correcting that literal is `audio/`'s to do.) The buffer is still ordered by audio time, now justified as defence in depth rather than as a response to observed behaviour. This correction was made before the record landed, by the pre-merge audit; nothing outside this branch ever read the false version. A fourth fact was caught by the multitenancy-guardian review of the I2 diff: `recording-stop-complete` is emitted **only by the tray's stop** (`tray.rs`); the ordinary stop path emits `recording-stopped` (`audio/recording_commands.rs`). The I1 panel listened to the tray event alone, and the first draft of I2 did too — which would have kept a finished meeting's transcript in memory until the next recording.

**Decision:**

- `copilot::session` treats **every** `transcript-update` as a final segment. `is_partial` is carried as `Turn.short_chunk` and decides nothing. A segment's identity is `sequence_id`; a re-emission replaces in place and never fires a second cue.
- Segments are ordered by **audio time** — defence in depth against `NUM_WORKERS` being raised again, not a response to present behaviour — and the rolling window is measured back from the latest segment *end*, not from the wall clock, so a pause in the meeting does not empty it. The window is a **view for building a prompt, not a retention bound**: nothing is evicted by it, and a meeting is resident in full while it is recorded.
- Channel attribution is an explicit `Channel::Unknown` until the pipeline carries it. `Channel::{Microphone, System}` and the rule "no cue from the user's own microphone" are implemented and tested **now**, against the value the producer will send, so that the day `source` becomes real nothing in the copilot moves. Populating `source` is an `audio/` change and stays out of EPIC I (CLAUDE.md §4); it is filed as BACKLOG **H13**.
- The panel's transcript tail shows every segment, unattributed.
- The session buffer is rebuilt at `recording-started` — re-resolving `AuthContext` there, so a Phase-2 tenant switch between two meetings cannot leave a buffer stamped with the previous workspace — and cleared on **both** stop events. The panel clears on both as well.
- The `copilot-cue` event carries ids and numbers only (`workspace_id`, kind, confidence, evidence `sequence_id`s); the consumer resolves them against the transcript it already holds. I3's consumer must drop a cue whose `workspace_id` is not its own.
- ADR-0038 finding 4 is **not** edited — accepted records are not rewritten; this record corrects it. BACKLOG I1/I2, `COMPETITIVE_CLUELY_GAP.md` §6 (the me/them row: ADOPT → DEFER) and `ROADMAP.md` Phase I are updated to say what the code does.

**Alternatives rejected:**

| Alternative | Why not |
|---|---|
| Implement the AC literally (drop partials, split me/them on `source`) | Drops most speech; invents an attribution the data does not contain. Both were caught only because the producer was read before the consumer was written. |
| Infer me/them from a heuristic inside the copilot (energy, device names in `timestamp`, voice) | Guessing a speaker from the signal is what ADR-0034 forbids; device-name heuristics have no data to work on. |
| Change `worker.rs` in I2 to send the real device | Correct fix, wrong place: the audio pipeline is the §4 high-risk zone and no EPIC I task may touch it (ADR-0038 invariant 2). It gets its own smoked change. |
| Keep the buffer in `sequence_id` order | Correct today (one serial worker), but it makes "the last 180 seconds" depend on a producer constant no consumer controls; audio-time ordering costs one `partition_point` per segment. |

**Consequences:** I3's prompt assembly must not rely on me/them, and its "Suggest" action cannot distinguish the user's own question from the counterpart's until H13 lands; the I8 proactive prefilter inherits the same limit. Any speaker-side feature in EPIC I depends on H13, which is an `audio/` task with the §4 manual smoke as its gate. The "no cue from microphone" gate is documented as inert where it lives (`session.rs` module doc).

**Status:** Accepted (2026-09-13). Implemented in I2 (`feat/i2-live-context`). Two producer facts in the first draft (three parallel workers; a 2 s live VAD) were false and were corrected above by the pre-merge audit before this record reached `main` — which is the same failure this ADR exists to prevent, caught one step earlier.

## ADR-0040 — The live window is redacted where it is built, and a live insight does not leave the device by default

**Context:** BACKLOG **I3a** (2026-09-13) adds the first model call in EPIC I: the copilot takes the rolling window built by I2 and asks a provider for one of I4a's four actions. Building it surfaced two facts that the I3 acceptance criteria assumed were already handled.

1. **The live window has never been redacted.** C6's opt-in redaction (`redaction::redact`) runs at two seams: the transcript write into SQLite, and the summary prompt. The live context is neither — `copilot::session` is built straight off the `transcript-update` stream and never touches the database. So an opted-in workspace's policy would have held on every surface *except* the one that speaks while the meeting is still happening, which is the surface where the conversation is freshest and the user is least able to check what left.
2. **A live insight is not a per-meeting provider decision.** The summary path's provider is chosen deliberately, once, for a meeting that has ended. A live insight fires from a global hotkey mid-sentence. Treating "which provider is configured" as consent to send the last minutes of a live conversation to a third party makes a privacy decision follow from a keypress the user set up for something else.

**Decision:**

- **Redaction happens at the prompt boundary, in `copilot::insight::window_passages`, and that function is the only path from a `Turn` to anything a prompt may contain.** A turn's `text` is never read directly by prompt assembly. Citation ids are derived from `sequence_id` alone (`passage_id`), so redaction rewrites the evidence text without breaking the link back to the segment — the HITL source-linking contract (docs/CONTRACTS.md §4) is preserved exactly as it is at the other two seams.
- **`CopilotConfig::allow_cloud_insights` defaults to `false`.** With it off, `generate_insight` refuses any provider it cannot *show* is local and returns `InsightError::CloudNotAllowed`; the built-in local model answers instead. `is_local_provider` is conservative and asymmetric: only `BuiltInAI` and `Ollama` are local, because locality is a property of the build for those two. `CustomOpenAI` is **not** local even with a `localhost` endpoint — the endpoint is user-supplied config that can change between the check and the request, so the policy would rest on a string rather than a fact. An unparseable provider name fails closed. The gate sits after the window is built and before the provider is assembled, so the user is told "not allowed" rather than "nothing to say", and no prompt carrying conversation text is ever handed to a provider the workspace did not allow.
- **An empty window is a refusal, and the model is not called.** `LiveInsightOutcome::NoContext` mirrors `AskOutcome::NoEvidence`: there is no "answered with nothing" variant, because an empty card reads as a statement about the conversation. A model consulted with an empty window would be answering from its own prior knowledge, which is the thing this epic promised not to ship.
- **`EvidencePolicy::Open` is declared but NOT honoured yet, and that is written down rather than implied.** Honouring it means a second grounding path that keeps unsourced model output — the one thing the epic's invariants exist to prevent — so it is not being added in the slice that introduces the first model call. Until it is, the one `Open` built-in (`lecture`) is grounded as strictly as a `SourceFirst` one. The failure mode is "the lecture copilot said less than it could have", not "something unsourced reached the user". A test asserts the equivalence so this record fails the day someone assumes leniency.
- **A prompt is capped at `MAX_PROMPT_TURNS` (40) and keeps the *recent* end**, reporting `turns_omitted` rather than silently truncating. The window is measured in seconds, so a fast meeting can overflow what the built-in local model will cope with; a live question is about now.
- **`prepare` is split out of `generate_insight`** so every refusal that happens before a model is consulted — wrong workspace, disallowed action, no readable source, empty window — is a unit test over data rather than something only an integration test can reach. Tenant mismatch between the live context and the caller's `AuthContext` is one of them (docs/MULTITENANCY.md rule 2: in-memory state is tenant state).
- **`AssembledProvider::call_cancellable`** is added alongside `call`, which now delegates to it with `None`. Every provider already honoured a `CancellationToken`; `call` simply never had one to pass. A live insight is abandoned on a 25 s timeout that also cancels the in-flight request, rather than leaving it to finish into nothing.

**Consequences:** The eight rules above are held by mutation-checked tests (removing the `redact` call, inverting the tenant check, letting an empty window through, keeping the oldest turns instead of the newest, using `allowed_sources` instead of `usable_sources`, dropping the action gate, defaulting the cloud policy to on, and treating `CustomOpenAI` as local each fail at least one test). Nothing in this slice is reachable from the UI: I3a registers no Tauri command and is called from nothing — I3b adds the panel, the Article 50 marking and "Pin to notes". The first model call therefore ships **unexercised against a real provider**; prompt assembly, the redaction boundary, the policy gate and grounding are proven by unit tests, but what a model actually returns for these prompts is an I9 live-smoke question and is not claimed here.

## ADR-0041 — "Pin to notes" cannot be built on the existing summary repository, and is split out of I3b rather than shipped broken

**Context:** BACKLOG **I3b** (2026-09-13) was specified with a "Pin to notes" action: one insight becomes a `draft` block carrying its `source_chunk_id`, written into that meeting's structured summary draft **through the existing C1 repository**, with the status forced to `draft`. ADR-0038 finding 3 says the same. Building the rest of I3b meant reading that path properly for the first time, and the specification turns out to rest on three premises that the code does not support. Each was verified directly, not inferred.

1. **There is no meeting row to write to while the meeting is happening.** `SummariesRepository::upsert_draft` refuses outright when one is missing (`summary_draft.rs:333-347`, `SummaryDraftError::MeetingNotFound`), and `edit_block`/`set_block_status` degrade to `Ok(false)`. The only production `INSERT INTO meetings` for a recording is inside `TranscriptsRepository::save_transcript`, which mints the id itself (`transcript.rs:35`, `meeting-{uuid}`) in the same transaction that stores the transcript — i.e. **after the recording ends**. During recording, `audio/recording_commands.rs` holds a pending recording with `meeting_id: None`. A pin during a live meeting would therefore fail 100 % of the time, not occasionally.
2. **The citation a pinned block would carry does not resolve.** Every block's `source_chunk_id` must point at a live `transcripts` row for that meeting (`ensure_sources_resolve`, `summary_draft.rs:215`), re-checked under the write lock. The copilot's evidence ids are `t{sequence_id}` (`copilot::insight::passage_id`) — synthetic, in-memory, and correct for the live window, where no `transcripts` row exists yet. There is no id-space bridge between the two, and building one is not a UI change.
3. **Even after the meeting is saved, the pin is guaranteed to be destroyed.** `upsert_draft`'s UPDATE binds `sections = ?` unconditionally from the caller's draft alone (`summary_draft.rs:397-402`); existing sections are never read first. `SummaryService` calls it with only the model's output (`summary/service.rs:1066-1073`). So the ordinary, unavoidable post-meeting summary — and every "Regenerate" after it — erases any pinned block, with no archive of the previous JSON and with `rev` bumped so it reads as a legitimate write. There is no append API anywhere on `SummariesRepository` to avoid this; the only suitable primitive, `write_sections_as_draft_if_current` (`summary_draft.rs:1150`), is private.

**Decision:**

- **"Pin to notes" is removed from I3b and filed as BACKLOG I3c.** I3b ships everything else in its acceptance criteria: the four actions, the Tauri command over `copilot::insight`, cancel and timeout, the Art. 50(1) disclosure and the non-dismissable Art. 50(2) marking, and a distinct rendering for every refusal. Nothing in I3b persists anything, which was already the epic's invariant 3 — the slice is now simply *entirely* non-persisting.
- **Shipping it against the current repository was considered and rejected.** The failure is not a rough edge: it silently deletes content the user hand-curated during their meeting, on a code path they cannot avoid taking. A feature that loses user-authored work is worse than an absent one, and "it usually survives" is not available here — the loss is certain, not probabilistic.
- **I3c's minimum design is recorded now so the next person does not re-derive it**: buffer pins in memory in `copilot::session` keyed by the `sequence_id` the live context already holds; flush at save time, once the meeting id and real `transcripts` ids exist and the `t{sequence_id}` → `transcripts.id` mapping can be resolved; add `SummariesRepository::append_block` on top of the existing private CAS writer rather than open-coding a second `sections = ?` writer; and decide how `upsert_draft` preserves non-generated blocks — either a provenance marker on `DraftBlock` (`generated` vs `pinned`) or an explicit merge. The last of those changes the `summaries.sections` JSON shape, so it needs its own ADR, a `docs/CONTRACTS.md` §4 update and a sync-compatibility note **before** any code.
- **ADR-0038 finding 3 is not edited.** Accepted records are not rewritten; this record corrects the "Pin to notes" half of it. What it says about marking, source linkage, grounding and refusal is unaffected and is implemented in I3a/I3b.

**Consequences:** The copilot can now answer during a meeting but cannot keep anything, which is a smaller product than I3 described and is stated as such in BACKLOG rather than left for a user to discover. The I9 gate must not be read as covering I3c. One thing improved on the way: the live context is no longer reachable as a borrowed value — `session::with_context` takes a synchronous callback, so the process-global mutex guard cannot be held across a model call, and `copilot::insight` was split into a synchronous `prepare` and an async `complete` to match.
